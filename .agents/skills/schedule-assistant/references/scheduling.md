# 统一日程生成规则

首次生成具体日程、为新增 Todo 排时间、重新安排受影响 Todo、重算某日关注顺序，或解释任务为何处于当前时间和顺序时，读取本文。

本文回答：给定正式 Todo、已经解释清楚的时间条件和当前 Schedule 后，哪些 Todo 还需要新增计划时间，应排到哪些合法时段，以及同一天的 Todo 应按什么顺序关注。

本文不建立 Goal、Node 或 Todo 结构，不解释日期和时间事实，不从执行反馈恢复进度，也不决定现实变化后哪些旧条目进入重排。

## 处理依赖

完整生成与交接流程统一见第 8 章。先确定保留/替换条目及可信进度，再计算覆盖和合法候选；第 3 章七组 Todo 的判断顺序与互斥条件必须保留。

## 按问题查找

| 当前问题 | 读取章节 |
| --- | --- |
| 为什么某个 Todo 没有进入待排 | 2～3 |
| 怎样计算已有未来条目覆盖了多少工作量 | 2 |
| 临时分组是否需要写成文件 | 2 |
| 一个 Todo 还需要新排多少分钟 | 3 |
| 本次排布使用哪些相关信息 | 4 |
| 多个合法 Todo 谁先排 | 5 |
| 怎样减少碎片、留出实际缓冲并权衡软偏好 | 5.1 |
| single_block、splittable 和 Habit 怎样排 | 6 |
| 当日关注顺序怎样生成和解释 | 7 |
| 完整 Schedule 怎样生成并交接提交 | 8～9 |

## 1. 生成前的必要输入

每轮排期至少读取：

- `TaskStructure` 中的 Goal、Node 和 Todo；
- 当前正式 `Schedule.entries`；
- 当前 `planning_window`、计划时区和计算时刻 `calculated_at`；
- AvailabilityRules、TimeConstraints 和受影响日期的日历分类；
- 当前处理所依赖的可信进度信息。

任务结构读取 `task-structure.md`，字段和正式数据读取 `plan-data-contract.md`，每天基础画像、TimeConstraint 展开和 Todo 合法候选时间读取 `calendar-and-time-rules.md`。

只为当前自然周生成新的正式具体日程，不提前生成以后各周。远期任务结构、周期模板和时间约束继续由其权威对象表达。

如果没有足以解释本轮日期的可用时间和已知承诺，不得生成看似精确到小时的正式日程。信息不足时是追问、只提供建议还是停止提交，读取 `decision-and-confirmation.md`。

任务语义与必要结构确认须在排期前解决，“简单日程”不降低要求。相关发现的范围、停止条件及 scheduling gate 见 [发现规则](discovery-loop.md)，候选校验与正式提交时序见 [提交操作](plan-write-workflow.md)。程序通过不证明理解或授权真实；纯局部修改不自动重做发现，首次门禁保留。

循环目标的普通节点任务、每期任务和直属任务都进入同一待排判断。未来周期或模板待定不阻塞已明确 Todo；节点的真实依赖、可开始日期和 DDL 按现有规则约束排期，周期身份不额外充当执行窗口。

### 1.1 正式周日程的就绪门槛

首次生成正式周日程，或后续相关事实改变时，候选 Schedule 需要：

- 已确立或已确认的任务结构，已按 [发现规则 §4～6](discovery-loop.md) 处理本次相关分支、结构及修复检查；未答问题不推成“没有”；
- 可信的当前剩余量、必要过去进度、依赖与协作条件；
- 所有相关非空 DDL 已确认到具体时刻；
- 能解释相关日期的计划时区、真实日历及完整可用画像；
- 已纳入本轮 TimeConstraint、日期例外和需保留条目；
- 没有会改变本次联合安排的关键未知或未授权取舍。

追问/确认的业务边界由 [确认规则](decision-and-confirmation.md) 维护。上述是输入结果要求，不要求局部改期重做首次访谈。

## 2. 运行时结果与未来覆盖量

本轮的七个 Todo 主分组、未来覆盖量、`minutes_to_schedule` 和 Schedule 校正要求共同构成运行时派生结果。它们可以存在模型当前上下文、内存对象、工具参数或一次性临时文件中，但：

- 不要建立固定的 `scheduling-backlog.json` 或其他正式业务文件；
- 不得写入 `plan.json`，也不得被解释为正式计划已改变；
- 只和用户讨论方案时，可以直接用自然语言推理和说明，不强制生成临时 JSON；
- 准备正式提交时，必须基于最新正式计划重新计算，再构造完整结构化候选计划。

Schedule 校正要求与七个主分组正交，例如清理 `terminal` Todo 的未来条目、减少 `overcovered` 条目，或替换不合法的 `single_block` 条目。它只表示生成完整候选 Schedule 时还要同步处理什么，不是新的持久化数据模块。能确定处理的校正直接进入完整候选；存在多种会造成不同用户影响的处理方式时，交给 `replanning-and-conflicts.md` 形成取舍方案，再按 `decision-and-confirmation.md` 判断授权。

先确定本轮的覆盖基线：

- 首次排期或纯新增排期时，基线是当前正式 Schedule 中尚未开始的 Todo 条目；
- 重新编排时，`replanning-and-conflicts.md` 先确定需保留和需移除或替换的旧条目；只有保留条目计入覆盖量，待替换条目不得继续冒充未来覆盖。

计算覆盖量前先确定性检查 `single_block` 的尚未开始条目：需要一个合法连续块，时长足以覆盖当前剩余工作量；覆盖不足、被拆成多块或已不合法时，将相关条目标记为待替换，不计入覆盖基线。超过估时不自动替换或缩短，先按第 3.6 节区分合理余量与重复、无意超排。

对覆盖基线扫描一次，按 `todo_id` 汇总尚未开始的 Todo 条目计划时长：

```text
entry_future_minutes
= entry.ends_at - entry.starts_at

future_coverage_minutes(todo_id)
= 同一 todo_id 的全部 entry_future_minutes
```

一个条目只在同时满足以下条件时计入覆盖量：

- `source_type = todo`；
- 引用的 Todo 存在；
- `starts_at > calculated_at`；
- 条目仍属于当前正式 Schedule，且本轮没有将它标记为移除或替换。

因此：

- 尚未开始的条目计入全部时长；
- 已结束条目对未来覆盖量贡献为 0，不能冒充实际投入；
- 正在进行的条目通常不进入本轮新增排期的覆盖量计算，而是冻结并继续占用日历；已确认中断后需要续排的例外见下文；
- TimeConstraint 不参与 Todo 工作量覆盖。

已过去条目的计划时长不自动从 `remaining_estimate_minutes` 扣除。实际还剩多少必须先按进度核对规则恢复事实。

**已确认中断后的续排例外：**用户确认实际执行、当前剩余量可信且允许拆分时，按 `replanning-and-conflicts.md` 第 5.4 节保留到中断边界的当前片段；它在 `calculated_at` 之后仍将执行的分钟数可计入本次计划覆盖。续排缺口为当前剩余量减去该未来片段和其他保留的未来覆盖，最低为 0。不能计入计算时点之前的分钟数，不能因此提前扣减 Todo 剩余量或标记完成。只有会后预计余量而无法确定当前全部剩余量时，先按进度规则判断是否需要补问；不把预测写成已发生事实。

### 2.1 截止前的漏排、少排提示

`validate_plan.py` 的 `required_coverage_gap` 扫描全部未结束、仍有有效归属路径或独立的 Todo，包括完全没有日程的任务。自身/有效上层 DDL 或原 `execution_window` 结束时间要求当前周结束前完成时，报告边界、剩余量、已排未来覆盖和缺口。已过去的分钟数不计入，重叠条目不重复累计；已结束、所有归属路径失效、仅在以后周到期的任务和未建立或已过期的周窗口不产生此提示。

这是基于当前数据的风险提示，不证明进度已核对、依赖已满足或任务已具备排期条件，也不授权调整无关事项。本轮已授权排期且需要在该边界前完成时，应复用可信事实补足安排，确有缺口才追问，排不下则说明冲突，不能将有缺口的安排宣称为已完整保障截止。仅录入事实或修改独立事项时，提示不强制阻断这项修改，也不扩大为全局重排；相关风险按实际影响简要说明。窗口结束与正式 DDL 分别说明，不能把前者改写成用户设定的截止。

## 3. 按固定顺序分组 Todo

每个 Todo 只进入以下一个主要分组，并必须按顺序判断：

### 3.1 `terminal`

条件：

- Todo `status` 是 `completed` 或 `cancelled`；或
- 所属 Goal/Node 已取消并使该 Todo 失效。

处理：不进入编排，并在本轮完整候选计划中清理其尚未开始的未来 ScheduleEntry；不得绕过候选、校验和原子提交直接改正式数据。

### 3.2 `in_progress_schedule`

条件：Todo 存在 `starts_at <= calculated_at < ends_at` 的正在进行 ScheduleEntry。

该时间判断不证明用户已经开始。用户明确该次完全未执行并要求改期时，先按 `replanning-and-conflicts.md` 第 5.3 节将原条目标记为待改期，不进入本冻结分组，也不因旧条目覆盖当前时刻生成已执行片段。

处理：在条目结束，或用户主动报告中断、提前完成之前，冻结该 Todo。不推断已完成多少，不重算待排工作量，也不新增补排条目。新确认的硬约束必然与条目的未来部分重叠时，交给 `replanning-and-conflicts.md` 第 5.4 节判断实际执行、中断边界及续排；信息已充分的续排退出仅冻结处理，按第 2 章例外计算缺口，再按后续分组和约束安排，不因仍有当前片段再次冻结整个 Todo。

用户在执行中报告中断、提前完成或取消时，先由 `progress-review.md` 更新权威进度事实，再由 `replanning-and-conflicts.md` 决定当前条目剩余时间如何释放和重排；本文不把原定时长当成实际投入。

### 3.3 `needs_progress_review`

条件：本轮需要为该 Todo 新增或重算具体日程，它存在全局核对范围内的已结束 ScheduleEntry，且本轮所需的真实状态或剩余工作仍未知。已明确报告且足以支持本次安排的可信反馈直接复用；正在进行条目不触发本分组。

处理：只暂停该 Todo 的新增排期，先读取 `progress-review.md` 取得当前处理所需的进度信息；询问范围取决于未知进度，不取决于移动条目数量。生成下一段滚动计划或真正的全局重排时仍完成完整核对，已明确覆盖的反馈不重复询问。局部复用反馈不推进全局确认点；无关事实、无关 Todo 和只读查询不因此被全局阻塞。

### 3.4 `deferred_or_blocked`

条件包括：

- 所属 Goal 已暂停，或所有非空归属路径都当前无效；
- Todo 原始弹性窗口与本轮 `planning_window` 没有交集；
- 必要前置 Todo 或有效归属节点的前置成果，在本轮窗口内无法形成可行的预计完成时间；
- 其他硬约束使 Todo 本轮不可执行。

处理：本轮不排，但保留 Todo 和原始事实，不将“本周不排”误解为取消或遗忘。下一轮重新计算。

如果前置 Todo 能在本轮窗口内先完成，后续 Todo 可以继续作为候选；其最早可排时间取前置 Todo 的预计完成时间，不必等到前置 Todo 已经是 `completed`。

### 3.5 `fully_covered`

条件：

```text
future_coverage_minutes = remaining_estimate_minutes
```

处理：已有未来 ScheduleEntry 已覆盖当前需求，不新增条目。

对 `single_block` Todo，总分钟数足够也不能代替连续性：必须由一个合法连续块完成。被分成多块或其他不合法的旧覆盖按第 2 章处理；带有合理余量的情况按第 3.6 节判断。

### 3.6 `overcovered`

条件：

```text
future_coverage_minutes > remaining_estimate_minutes
```

处理：不再追加工作覆盖，先判断超出的原因。估时 60 分钟、安排 70 分钟可能是合理余量，两种执行模式均由 `future_coverage_exceeds_remaining` 提醒，不仅因数字超额拒绝。合法且有实际用途的余量可保留，不把估时改大来消除提醒；同一遍工作误排两遍、过期副本或无意超排应按授权校正，不能用“缓冲”解释重复任务。难以确定用户意图且会影响安排时再补问。

余量仍受 DDL、窗口、占用、依赖和连续性约束，不替代取消、缩减其他工作等重大取舍的授权。缩短、移除或保留的具体处理继续按 `decision-and-confirmation.md` 判断；warning 不是自动忽略，也不等于一律要求用户再确认。

### 3.7 `scheduling_backlog`

条件：Todo 当前可执行，且：

```text
future_coverage_minutes < remaining_estimate_minutes

minutes_to_schedule
= remaining_estimate_minutes - future_coverage_minutes
```

只有这个分组会作为本轮新增或替换排期的候选交给编排器。`minutes_to_schedule` 不得小于 0，表示当前尚未被保留日程覆盖的净工作量；若另留余量，必须按第 3.6 节判断用途和影响。它不表示所有 `splittable` Todo 都必须在本周排完。

`single_block` 因旧覆盖不合法而进入本分组时，本轮不是在旧条目上追加差额：应替换相关旧条目，并为当前全部 `remaining_estimate_minutes` 重新形成一个连续块。

Habit 进入本轮排期前，先按任务结构 §9 检查相关周期的应有实例，复用并补齐缺少的 Todo，再执行上述分组；不能仅遍历当前 todos 就把尚未展开的习惯遗漏。当前周期全部未结束 Habit Todo 都必须参与上述分组。用户额外增加的当期 Habit 次数即使不改变 `minimum_count`，对应 Todo 也必须进入本轮待排工作量判断。

## 4. 本次排布使用的相关信息

完成分组后，模型围绕 `scheduling_backlog` 中的 Todo 和必要上下文决定本次排布；这些是运行时信息，不要求另建编排服务或准备文件：

- Todo 标题和当前剩余工作语义；
- `minutes_to_schedule`；
- 与该 Todo 相关的 Schedule 校正要求，包括哪些旧条目需保留、移除或替换；
- 运行时有效可排窗口和合法候选时段；
- Todo 自身及有效归属路径的 DDL；
- 相关前置、可解锁的后续 Todo 和 Goal `priority`；
- `execution_mode`、`intensity` 和 Habit 软硬偏好；
- 当天精力画像、TimeConstraints 以及本轮需要保留的已有条目。

本次排布不把 `terminal`、无关长期 Todo 或完整历史都当作待安排对象；仍读取正式计划，并对完整候选校验。模型不得改写确定性分组、未来覆盖量或 `minutes_to_schedule`；对 `splittable` Todo，可以根据本轮容量在 `0..minutes_to_schedule` 内决定覆盖多少净工作量，另留余量按第 3.6 节处理。程序化校验仍对完整候选负责。

## 5. 在合法候选中决定排布

排布前先排除任何会产生以下结果的候选：

- 与 TimeConstraint 或需保留的 ScheduleEntry 冲突；
- 位于 Todo 运行时有效窗口之外；
- 违反依赖顺序；
- `single_block` 无法容纳当前全部剩余工作量的一个合法连续块；
- 突破默认 AvailabilityRules 且没有该具体条目的合法 `availability_exception`；
- 会导致已确认 DDL 不可满足或其他硬约束冲突。

只在合法候选中综合以下层次作决定：

1. 优先保护已经逼近 DDL、继续延迟将导致无解的条目。
2. 其次优先能解锁后续 Todo 或处于关键交付路径的条目。
3. 可行性相近时，优先更高 Goal `priority`。
4. 再考虑弹性窗口剩余余量、待排工作量、精力匹配、上下文切换和对现有日程的扰动。

Goal `priority` 表示跨日、跨周的长期相对重要性，不表示紧急程度。一个临近硬 DDL 的 P1 可以先于暂时没有时间压力的 P0；P0 也不能授权系统违反 DDL、依赖、TimeConstraint 或可用容量。

在 Goal 长期相对重要性这一层内，`P0 > P1 > P2`：P0 是容量冲突时优先保护的目标，P1 是正常重要，P2 是容量不足时相对可让步。这组领域优先级不等于开发范围的功能 P0/P1/P2。

不要把上述层次强制实现成固定数字评分。AI 可以结合语义判断，但必须能说明主要压力来源，并由确定性校验保证硬约束。

共享 Todo 只从当前有效归属路径读取最高 Goal `priority` 和最早非空 DDL。多条归属可以提高其解锁价值，但不得为同一行动重复生成日程或重复计算工作量。

本轮只在当前 `planning_window` 内分配时间。对 `splittable` Todo，可以只安排当前窗口能合理容纳的一部分；本轮实际新排量直接从候选 ScheduleEntry 汇总，不新增持久化字段。如果 Todo 的 DDL 或有效窗口要求它必须在本轮窗口内完成，则候选 Schedule 必须完整覆盖届时所需的剩余工作量；排不下时进入冲突处理，不能用部分安排伪装成可行。

### 5.1 连续工作、缓冲与软偏好的取舍

在第 5 章的硬约束和交付压力之内，比较安排是否方便实际执行；不为这些软因素设统一分数、最短时间块或缓冲比例。只优化本轮已授权的待排/替换范围，既有合法安排的稳定性本身有价值。

- **减少无谓拆分。** `splittable` 表示允许拆分，不表示应该拆分。任务需要持续理解或创作，且存在不挤占更紧迫工作、能在截止前完成的整块时段时，优先连续安排，不因较早空档可用就留下低价值尾段。确有容量、依赖、协作或精力收益时可以分段；真正只需十分钟的行动仍可排十分钟，不通过拉长估时或省略任务来避免短块。
- **合并有边界。** 同一 Todo 的相邻尚未开始片段，在本轮允许调整、执行条件及条目例外相容时可合并，保持 Todo 身份并沿用一个原条目 ID；不能把无关任务合成新任务、吞掉有用途的间隔，或越过硬占用。用户要求保留具体片段、历史或正在执行的片段时，继续遵守保留规则，不为合并扩大影响范围。
- **缓冲体现在空档。** 会议密集、任务切换或已知收尾需求较多且容量允许时，在受影响排布中留出可用于转换和机动的空档；比较空档所在位置是否真能发挥作用，不只看当天空闲总分钟数。普通机动余量保持为空闲，不凭空新建“缓冲 Todo”、硬 TimeConstraint 或缩窄 AvailabilityRules。任务时间块内部的估时余量另按第 3.6 节处理，不能把同一时间既算作任务覆盖又说成空闲。
- **缓冲服从可行性。** 依据已有执行背景、连续占用和交付压力判断余量，不因没有精确缓冲分钟数就追加问卷。若留空会导致已确认截止无法满足，不静默漏排、延后或缩减工作；当前硬约束内可排满时可以排满，并简要说明没有机动余量。用户明确规定的休息、通勤或不可用时间仍是原有硬约束，不能作为可牺牲缓冲。
- **软偏好用于选择。** 在交付可行性相近的候选中，优先满足用户时段偏好和精力匹配、减少上下文切换；不能为追求这些因素改动原窗口、DDL 或无关安排。只有非偏好时段可满足硬边界时，可选该合法时段并说明主要取舍；已有默认可用范围内偏离软偏好不需要 `availability_exception`。若用户表达的是明确禁止，按时间规则处理，不能反向降级为偏好。

提交前对照实际条目核实本次声称的改善：连续性是否真的改善，缓冲是否确实空着，短任务是否仍有覆盖，偏好未满足时是否有具体原因。回复只说明有意义的结果与取舍，不逐项输出内部检查过程。

## 6. 执行模式、Habit 偏好和覆盖校正

### 6.1 `single_block` 和 `splittable`

- `single_block` Todo 必须用一个连续时间块覆盖当前剩余工作量，不能以总时长足够为由拆成多个块。
- `splittable` Todo 可以对应一个或多个 ScheduleEntry；硬边界未要求本周完成时，本轮可只排一部分。
- 两种模式的排期均以可信剩余量为基准，超过估时的余量按第 3.6 节判断；合理余量不改变任务工作量，不豁免其他硬约束。

`single_block` Todo 已有的未来覆盖只有一部分、被拆成多个块，或无法与新时间合并为一个连续块时，不能简单再追加一个块。应将它作为 Schedule 校正，为当前全部剩余工作量重新形成一个合法连续块；如果无法形成，不得伪造已完整覆盖的日程。

### 6.2 Habit 偏好

Habit 专属的长期星期和时段偏好由 `habit_rule` 提供：

- `required` 偏好作为硬候选边界，不满足的时段不可用；
- `preferred` 偏好作为软排序信号，应尽量满足，但不满足不使日程非法；
- 当期 Todo 的临时 `execution_window` 始终参与合法性计算；
- 用户对所有任务普遍适用的作息仍来自 AvailabilityRules。

### 6.3 精力匹配

高强度 Todo 与低精力时段不匹配属于软排序信号。可以降低该候选的优先度并向用户说明，但不因此判定 ScheduleEntry 非法，也不需要为精力不匹配保存 `availability_exception`。

## 7. 生成当日关注顺序

每次生成或重新编排 Schedule 时，必须运行 `scripts/rank_plan.py`，对每个自然日内所有 `source_type = todo` 的 ScheduleEntry 生成从 1 开始、唯一且连续的 `daily_rank` 和对应 `priority_reason`。`1` 表示当天最应保护注意力的安排，不表示最早开始，也不自动表示此刻可执行。

- `daily_rank` 只在同一日期内比较，不跨日期排名；
- TimeConstraint 条目不参与排名，仍按固定时间展示；
- `Schedule.entries` 数组顺序不承载执行顺序语义；
- 同一 Todo 同日有多个时间块时，每个 ScheduleEntry 都是独立的当日顺序项；
- `daily_rank` 不替代 `starts_at` 和 `ends_at`，也不替代当前可行动性判断；固定时间未到或当前依赖未满足的条目不会因此提前执行；
- 不得按 `starts_at`、数组顺序或 viewer 展示顺序直接生成排名；开始时间只能在所有语义信号相同后作为稳定兜底。

确定性排序按以下层次比较：

1. 有效 DDL 压力：已到、24 小时内、7 天内、较远、无 DDL；同档取更早的有效 DDL。
2. 依赖与解锁价值：能解锁更多未结束后续 Todo 的条目优先；同日存在前置与后续时必须保持拓扑顺序，包括通过有效节点依赖连接的行动；这些关联只在运行时展开，不复制为持久化 Todo 依赖。
3. 有效归属路径中最高 Goal `priority`，按 `P0 > P1 > P2`；独立行动按正常重要性处理。
4. 弹性时间窗余量，窗口更早收窄的优先。
5. 只有以上相同才按 `starts_at` 和条目 ID 稳定排序。

`priority_reason` 必须由同一排序模块生成，说明实际生效的 DDL、解锁价值和目标优先级，不得用“时间更早”冒充关注原因。`validate_plan.py` 会重新派生顺序并做硬比较；连续但语义错误的排名同样非法。

用户明确要求覆盖某日关注顺序时，不把该偏好写成 Todo 或 Goal 的永久优先级。该日每个 Todo ScheduleEntry 都必须保存内容相同的 `ranking_exception = {confirmed_at, reason}`，从而明确这是用户覆盖而不是算法漏算；局部、无理由或不同内容的覆盖非法。是否可直接提交本次变化，继续按 `decision-and-confirmation.md` 判断。

## 8. 完整 Schedule 生成顺序

一次完整生成或重新编排按以下顺序处理：

```text
0. 确认任务语义、对象分类、新结构确认和提交前语义质量检查已经完成
1. 从正式任务结构中初步筛选本轮相关 Todo
2. 确定需保留、移除或替换的旧条目，汇总保留条目的未来覆盖量
3. 展开当前 planning_window 内的 TimeConstraint occurrence
4. 按日期画像、Todo 有效窗口和硬占用生成合法候选时间
5. 结合状态、进度门槛、时间可行性和未来覆盖量，按第 3 章的固定顺序完成分组
6. 使用 scheduling_backlog 和相关 Schedule 校正要求决定排布
7. 在当前 planning_window 内生成新条目或替换条目，splittable 允许只覆盖部分剩余工作量
8. 将 Todo 条目、TimeConstraint 投影和需保留条目汇总为完整候选 Schedule
9. 运行 `scripts/rank_plan.py`，为每个日期的全部 Todo 条目生成关注顺序和理由
10. 校验时间、引用、连续性、依赖、DDL、容量和关注顺序；处理覆盖缺口与超额提醒
11. 按提交流程和当前授权提交，或展示整组方案等待用户确认
```

候选、rank、validate/apply 的具体调用统一见 [提交操作](plan-write-workflow.md)。首次排期和重新排期共用上述排布和校验规则。两者的差别在于：重排前由 `replanning-and-conflicts.md` 先确定受影响集和需要保留的条目；每周首次正式排期能否直接提交，由 `decision-and-confirmation.md` 决定。

后续新增或重排涉及其他 Todo 的普通连带改期时，统一按该文第 5.1 节判断授权，不因移动本身额外确认，也不把候选校验通过视为已获授权。

## 9. 结果解释与失败边界

排期后的通用说明按 [确认规则 §10](decision-and-confirmation.md)。本场景按实际影响补充：哪些任务进入日程及主要安排原因；需要用户留意的阻塞、容量压力或未覆盖工作；部分安排是否足以保障本轮硬边界；连带移动的关键影响。简单单项无需逐条复述这些类别。

`priority_reason` 由排名模块生成，不能代替业务解释，也不是新的权威任务事实。

如果在已有硬约束内无法形成完整可执行日程，不得伪造看似已完整覆盖的 Schedule，也不得自行改动 DDL、承诺或任务去留。冲突识别和取舍方案读取 `replanning-and-conflicts.md`，确认权限读取 `decision-and-confirmation.md`。
