# 重新编排、影响范围与冲突处理

现实变化影响已有任务或日程，Todo 进度、工作量、依赖、DDL 或时间窗变化，用户要求局部或整体重排，或当前计划可能无解时，读取本文。

本文回答：一项变化需要重新计算哪些对象，哪些旧 ScheduleEntry 应保留、移除、替换或冻结，影响范围应如何扩大，以及现有约束内无解时如何形成取舍方案。

本文不重新定义 Todo 的具体排布算法，不恢复过去进度，不自行修改 DDL、承诺或任务去留，也不直接写入正式计划。

## 主流程

```text
1. 重新读取正式计划，合并本轮已明确的原始变化
2. 判断当前处理是否依赖未知的过去进度
3. 建立初始影响集，将旧条目分为保留、移除、替换或冻结
4. 沿同一 Todo、时间冲突、容量和依赖逐层扩大影响范围
5. 将受影响 Todo、保留条目和待替换条目交给 scheduling.md
6. 对完整候选进行全局校验；可行时停止扩圈
7. 仍无解时保持正式计划不变，形成少量有实质差异的取舍方案
8. 根据用户授权直接提交，或等待用户选择后重新计算并原子提交
```

## 1. 现实变化与重新编排

现实变化是使正式计划所依据的任务、进度、时间或约束发生改变的新事实。它可以来自用户明确修改，也可以来自进度核对后恢复的可信当前状态。

重新编排是在不篡改这些权威事实的前提下，确定其未来影响，保留仍然有效的日程，只重算必要的条目，并恢复一份可执行候选计划的过程。

一条用户输入可以同时包含多个变化。先将它们合并成同一份候选变更，再统一分析影响；不要在每个子变化后反复写入 Schedule。

重新编排只生成、移除或替换当前 `planning_window` 内的具体 ScheduleEntry：

- 如果 `planning_window = null`，说明尚未建立本周正式计划，应转入 `scheduling.md` 的首次排期，而不是按已有计划重排；
- 如果变化只影响当前窗口之外的未来时间，更新对应权威事实，但本轮不提前生成未来周的具体 ScheduleEntry；
- 当前窗口之外的影响可以作为风险或后续事项向用户说明，但不能借此扩大排期范围。

修改正式事实的权威字段读取 `plan-data-contract.md`；恢复 Todo 过去进度读取 `progress-review.md`；日期、可用时间和占用语义读取 `calendar-and-time-rules.md`。

## 2. 运行时影响计划

本轮可以在内存、工具参数或一次性临时结构中表示一份影响计划，至少区分：

- `changed_facts`：本轮已获得授权或正在提案中的原始事实变化；
- `affected_todo_ids`：需要重算未来覆盖、时间或排名的 Todo；
- `entries_to_keep`：本轮必须保留的旧 ScheduleEntry；
- `entries_to_remove`：源对象已失效或已明确不再需要的未来条目；
- `entries_to_replace`：仍有对应工作，但时间、时长、覆盖或合法性需要重算的条目；
- `entries_to_freeze`：当前正在进行、用户未报告中断、提前完成或取消，并且没有新硬约束必然切断其未来部分的条目；
- `unresolved_conflicts`：当前约束内无法吸收的冲突及其原因。

这些都是运行时派生结果，不写入 `plan.json`，也不要为它们建立固定业务文件。只讨论方案时可用自然语言表达；准备提交时再基于最新正式计划重新计算完整候选。

`entries_to_freeze` 是 `entries_to_keep` 中更严格的子集：保留条目只是本轮不应被重算，冻结条目则在得到中断、提前完成或取消反馈之前不得移动或补排。新确认的硬约束必然切断正在进行条目的未来部分时，该条目退出冻结集合，并只按 5.4 处理冲突部分。

## 3. 从原始变化建立初始影响集

| 原始变化 | 初始影响集 |
| --- | --- |
| 新增或扩大 TimeConstraint | 与新占用重叠的 Todo 条目；必须依赖被占容量才能满足近期硬边界的 Todo；若与正在进行条目的未来部分重叠，按 5.4 处理 |
| 取消、缩短或改期 TimeConstraint | 对应 TimeConstraint 投影和替代时间与其他条目的新冲突；释放的空闲时间不默认触发填满 |
| AvailabilityRules 或 `date_overrides` 变化 | 受影响日期上已不合法的 Todo 条目，以及容量缩减后无法满足近期硬边界的 Todo |
| Todo 完成或取消 | 该 Todo 的未来条目、依赖它的后续 Todo，以及相关 Node/Goal 状态 |
| Todo 部分完成、未完成或剩余估时变化 | 该 Todo 的未来条目和覆盖量；预计完成时间改变时扩展到依赖后续 |
| Todo 的依赖、`execution_window`、DDL 或 `execution_mode` 变化 | 该 Todo 的所有尚未开始条目，以及依赖闭包中预计完成时间发生变化的后续 Todo |
| Goal `priority` 变化 | 该 Goal 有效路径上 Todo 已排入的日期；先用 `rank_plan.py` 重算相关关注顺序，只在容量或硬边界需要时移动具体时间 |
| Goal/Node 暂停、恢复、完成、取消或结构改变 | 通过受影响归属路径到达的 Todo；共享 Todo 还要保留其他有效路径的约束和日程需求 |
| 用户只调整某日关注顺序 | 该日全部 Todo 条目、`daily_rank` 和统一的 `ranking_exception`；不修改 Goal/Todo 长期优先级 |
| 用户明确要求局部或整周重排 | 以用户明确指定的 Todo、日期或整周作为初始范围 |

任何条目移除、缩短或改期后释放的容量都不默认触发“把空闲时间填满”。只有当前请求本身包含重新优化、某个已受影响 Todo 需要恢复覆盖，或现有 DDL/窗口要求必须使用该容量时，才将它作为新候选时间。

如果当前变化需要某个 Todo 的真实剩余工作才能继续，且它存在尚未核对的已结束条目，先按 `progress-review.md` 进行局部询问。如果影响已扩展到整体重排，先完成完整进度核对。无关事实不因其他历史未核对而阻塞。

## 4. 最小必要扩圈

影响范围从第 3 章的初始集开始，按以下顺序扩大。每层都尝试生成候选并对整份计划校验；一旦可行且没有新的连带影响，就停止扩圈。

### 4.1 同一对象与同一 Todo

1. 先处理原始变化直接引用的 Goal、Node、Todo、TimeConstraint 或 AvailabilityRules。
2. 纳入同一 Todo 需要一起检查的全部尚未开始条目，避免只移一块后覆盖量或 `single_block` 语义失真。
3. 完成、取消或归属路径失效时，先判断该 Todo 是整体失效，还是仍有其他有效路径。

### 4.2 同日冲突与容量

1. 将与新硬占用直接重叠、因可用时间改变而不再合法，或与新候选冲突的 Todo 条目纳入影响集。
2. 优先在原日期、原 Todo `execution_window` 和现有硬约束内吸收变化。
3. 关注顺序的最小一致性边界是该日全部 Todo 条目；用 `rank_plan.py` 重算，但不因此移动其他条目的具体时间。
4. 只有当局部条目无法在不占用其他已安排 Todo 时间的情况下重排，才将相关容量竞争者纳入下一层候选影响集。

### 4.3 依赖和上层路径

1. 预计完成时间变化后，反向扫描全部 Todo 的 `depends_on_todo_ids`，纳入全部直接和间接后续。
2. 对共享 Todo，分别检查每条有效 `parent_ref` 上的 Node 和 Goal DDL，以及哪些路径因暂停、完成或取消而不再参与当前排期。
3. 只传播实际改变预计完成时间、有效窗口、容量或上层硬边界的影响；不因对象在同一 Goal 下就无条件扩大到全部同属任务。

### 4.4 扩大到整周的条件

只在以下情况扩大到当前整个 `planning_window`：

- 用户明确要求整周重排；
- 受影响 Todo 的合法候选跨越多日，局部日期内无法恢复可行性；
- 多个 Goal 之间的容量取舍无法在更小范围内判断；
- 依赖影响已跨越多日，或受影响 DDL 覆盖本周余下窗口；
- 正在生成新一段滚动周计划。

即使扩大到整周，也不代表可以改动每个条目。未受影响的条目继续作为保留输入，只在给定影响集无法产生合法完整候选时继续扩大。

扩大到当前整个 `planning_window` 后，若完整候选仍无法通过全局校验，停止扩圈并进入第 8、9 章。不得继续排到下一周，也不得擅自放宽硬约束、DDL 或用户承诺来制造可行方案。

## 5. 旧 ScheduleEntry 的处理

MVP 的 ScheduleEntry 不保存 `locked` 字段。条目是否保留由它是过去、正在进行、TimeConstraint 硬投影、未受影响，还是已进入本轮移除或替换集合决定。不得凭空假设某个未来 Todo 条目被锁定，也不得因为数据里没有锁定字段就默认移动全部未来条目。

### 5.1 必须保留

- 已结束的过去条目，除跨周成功提交时按历史保留策略统一清理外，不因普通重排改写；
- 当前正在进行的 Todo 条目，在用户未报告中断、提前完成或取消时冻结；新确认的硬约束必然切断其未来部分时，按 5.4 的窄范围中断规则处理；
- 未受本轮变化影响且仍然合法的未来 Todo 条目；
- 仍有效的 TimeConstraint 权威投影。

对未受影响的 Todo ScheduleEntry，尽量保留原 `id`、`starts_at` 和 `ends_at`。新增、删除、DDL、依赖、Goal 优先级或窗口发生变化时必须重算相关日期的关注顺序；不能为了保持旧顺序而违反新的确定性语义。

### 5.2 移除

以下尚未开始条目进入 `entries_to_remove`：

- Todo 已完成或取消，且条目已不再需要；
- Todo 因上层路径失效且没有其他有效归属而不再参与当前排期；
- TimeConstraint occurrence 因取消、`skip` 或规则变化而不再存在；

完成、取消或路径失效并不删除 Todo 对象本身；对象保留规则读取 `task-structure.md`。

### 5.3 替换

以下尚未开始条目进入 `entries_to_replace`：

- 与新的 TimeConstraint 硬占用重叠；
- 已位于新的合法候选时间之外；
- 违反更新后的依赖顺序、有效 DDL 或运行时有效窗口；
- Todo 剩余工作量或 `execution_mode` 变化，使已有覆盖需要校正；
- `single_block` 的已有未来覆盖不再是一个完整合法连续块；
- 用户撤销了该条目的单条可用时间例外，且原时间不能在默认可用范围内继续保留；
- TimeConstraint occurrence 被改期，或循环规则变化后需重建投影。

待替换 Todo 条目不得继续计入 `scheduling.md` 的未来覆盖基线。对应 Todo 保留原 `todo_id`，只重新生成具体时间。

### 5.4 正在进行条目的剩余时间

ScheduleEntry 表示计划，不是实际执行日志。用户事后说明自己更早停止时，该反馈用于 `progress-review.md` 恢复 Todo 进度，不反向把已经过去的计划截断到实际停止时刻。普通中断、提前完成或取消从本轮 `calculated_at` 开始释放尚未发生的容量：

- `calculated_at` 位于原条目中部时，在候选 Schedule 中将 `ends_at` 缩短到 `calculated_at`；
- `calculated_at` 不晚于 `starts_at` 时，移除整个尚未开始条目；
- 不修改 `calculated_at` 之前的计划历史，也不据此推断实际投入时长。

新确认的 TimeConstraint 或其他硬占用与正在进行条目的未来部分重叠时，视为当前任务将在硬占用开始处中断：

1. 中断边界取不早于 `calculated_at` 的硬占用开始时刻；
2. 保留边界之前的当前条目，只释放与硬占用冲突的未来部分；
3. 向用户确认当前 Todo 是否还需要另留一段时间完成；如果需要且原剩余估时已不可信，再询问大约还需多久；
4. 只将该 Todo、直接冲突条目和预计完成时间确实变化的依赖后续纳入小范围重排；
5. 除非局部候选仍无法通过全局校验，不扩大到整日或整周。

这类截断只调整当前计划从计算时刻之后的可执行部分，不建立实际耗时日志。用户是否已经完成、还剩多少工作，仍以 `progress-review.md` 更新后的 Todo 事实为准。

### 5.5 `availability_exception`

未受影响且时间未改变的条目保留原 `availability_exception`。条目移动后：

- 新时间回到默认可用范围时，删除旧例外；
- 新时间仍需突破默认可用范围时，不复制旧确认，按 `decision-and-confirmation.md` 重新获取针对新时间的授权；
- 例外仍不能穿过 Todo 有效窗口、DDL、依赖或 TimeConstraint。

## 6. 依赖延迟的传播顺序

前置 Todo 延迟、部分完成或未完成时，按以下顺序处理：

```text
1. 根据用户反馈恢复上游 Todo 当前状态和剩余工作
2. 重算上游 Todo 的未来覆盖和预计完成时间
3. 反向扫描 depends_on_todo_ids，找出所有直接和间接后续
4. 对共享 Todo 分别检查每条有效归属路径的 Node 和 Goal DDL
5. 按 calendar-and-time-rules.md 重算后续 Todo 的运行时有效窗口
6. 在不改动原始 execution_window 和已确认 DDL 的前提下局部重排
7. 对整份候选计划校验依赖、容量和各层 DDL
```

后续 Todo 的原始 `execution_window` 不因前置延迟自动改写。只把有效开始推迟后形成的窄窗口作为运行时派生结果。如果窄窗口内仍有可执行方案，交给统一排期；如果无法满足，不得通过静默改写原窗口或 DDL 伪造可行。

## 7. 交给统一排期

完成影响分析后，向 `scheduling.md` 提供：

- 当前 `planning_window` 和本轮计算时刻；
- 更新后的权威 Todo、TimeConstraint 和 AvailabilityRules 候选事实；
- `affected_todo_ids`；
- `entries_to_keep`、`entries_to_remove`、`entries_to_replace` 和 `entries_to_freeze`；
- 依赖闭包、有效上层路径和需要重算的日期；
- 本轮用户明确授权的原始动作范围。

`scheduling.md` 只对待排 Todo 和需要替换的条目生成具体时间，保留条目继续作为硬占用输入。待移除或待替换条目不得继续冒充未来覆盖。

新候选生成后，必须对完整计划而不是只对局部片段进行校验。如果候选仍造成新重叠、覆盖异常、依赖违反或 DDL 风险，将新受影响对象加入影响集并继续第 4 章；没有新影响且全局校验通过时停止。

## 8. 无解与信息不足

至少识别以下无解情况：

- 在某个已确认 DDL 或硬窗口前，必须完成的总工作量超过合法可用容量；
- 多个 DDL 和工作量在现有容量下无法同时满足；
- 前置 Todo 的最早可行完成时间已晚于后续 Todo 的有效结束或 DDL；
- TimeConstraint 硬占用、Todo 有效窗口和 AvailabilityRules 的交集中没有合法位置；
- `single_block` Todo 在其必须完成的有效时间窗和 DDL 内，找不到覆盖当前全部剩余工作量的连续时段；
- 两个或多个已确认硬条件互相矛盾。

对 `splittable` Todo，如果 DDL 和有效窗口都不要求它在当前 `planning_window` 内完成，本周只能安排一部分不等于无解；只需如实说明本周覆盖和剩余未覆盖工作量。

无法确认工作日分类、用户指代、剩余工作量或其他必要事实时，这是信息不足，不是无解。按对应领域 reference 进行最少必要追问；不得用猜测的输入制造虚假冲突或伪造可行日程。

确定无解时，不生成看似完整的虚假 Schedule，不重叠排期，不静默越过 DDL，也不默认用户可以额外熬夜或改动承诺。

## 9. 形成重大取舍方案

现有硬约束内无解时，保持正式计划不变。回复中先明确说明“当前约束下没有可执行计划”，再说明主要冲突并提供少量有实质差异的方案。不要把同一个取舍换不同措辞列成多个方案。

可用取舍方向包括：

- 延长 Todo 原始弹性时间窗；
- 将行动拆分得更具体，或经用户选择后改变 `execution_mode`；
- 减少、取消或替换已不再必要的工作；
- 调整 Todo 顺序，或解除已确认不再成立的依赖；
- 修改 Todo、Node 或 Goal DDL；
- 增加可用时间、明显提高单日负担，或为特定 Todo 请求可用时间例外；
- 移动、缩短或取消日程承诺。

每个方案都要让用户看懂：

1. 具体改变什么；
2. 它解决哪个冲突；
3. 影响哪些任务、日期、工作量或承诺；
4. 仍然存在什么风险或不确定性。

可以给出推荐方案，但不能替用户静默选择牺牲对象。哪些变化属于必须确认的重大取舍，读取 `decision-and-confirmation.md`。

## 10. 授权、提交与说明

本文只确定变化影响了什么和形成哪些可行候选；是否已经获得授权，以 `decision-and-confirmation.md` 为准。

可以直接提交的典型情况：

- 用户明确要求的对象及时间范围内重排，完整结果没有超出该授权；
- 已获得明确进度反馈后，只在同一 Todo 原 `execution_window` 和现有硬约束内更新它的未来条目；
- 原始变化和新日程可以使用空闲容量吸收，不改动其他任务或承诺；
- 用户已明确指定本次需要移动、取消或修改的对象，且没有新的未授权连带代价。

需要先展示整组方案的典型情况：

- 为吸收原始变化，必须移动、压缩、取消或推迟用户未授权改动的其他任务；
- 需要修改 DDL、承诺、任务去留、已约定结果或明显增加负担；
- 无法可靠判断应该让哪个事项承担代价；
- 原始变化与派生重排需要作为一个不可分割的取舍处理。

等待用户确认时，原始变化和全部派生重排都不写入正式计划。用户确认后，重新读取最新正式计划并重新计算完整候选；如果新结果与已确认方案不再业务语义等价，必须重新展示并确认。

成功提交后，至少说明原始事实和日程实际改了什么、哪些条目被保留或移动、对其他任务和日期的关键影响，以及是否仍有需要用户留意的风险。

## 11. 跨周滚动

跨周生成不是普通局部重排，但仍使用相同的影响集、排期和全局校验原则。

```text
1. 按 progress-review.md 完成确认点之后的全部待核对过去进度
2. 在候选数据中更新 Todo、上层状态和 progress_reviewed_through
3. 按 task-structure.md 幂等生成新当前周所需的周期结构
4. 按 calendar-and-time-rules.md 恢复新周时间事实和合法候选
5. 按 scheduling.md 只生成新当前自然周的正式具体日程
6. 在同一候选中清理早于上一自然周的 ScheduleEntry
7. 完整校验通过后原子提交全部结果
```

用户未完成完整进度核对的兜底确认时，不得清理旧条目或生成新周正式计划。新周生成、校验或提交任一步失败时，进度结果、确认点、新 Schedule 和历史清理全部不生效，原正式计划保持不变。

## 12. 结果与不变量

一次重新编排的运行时结果至少要能解释：

- 原始变化是什么；
- 初始影响对象和最终扩大范围；
- 哪些条目保留、移除、替换或冻结；
- 是否在现有约束内可行；
- 如果无解，主要冲突和可选取舍是什么。

始终保持：

- 不因为一项变化就默认整周重排；
- 未受影响条目尽量保留 ID、具体时间和相对顺序；
- 已结束条目不被普通重排改写，尚未核对的过去条目不得提前清理；
- 正在进行条目在没有明确反馈时冻结；
- 取消或缩短时间占用后不默认填满释放时间；
- 后续 Todo 的原始时间窗和 DDL 不因依赖延迟被静默改写；
- 待移除或替换条目不得继续冒充未来覆盖；
- 局部候选必须通过完整计划的全局校验；
- 无解时不生成虚假 Schedule，也不修改正式计划；
- 需要用户取舍时，原始变化和派生重排在确认前全部不生效。
