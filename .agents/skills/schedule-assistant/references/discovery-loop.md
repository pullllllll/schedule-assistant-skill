# 多分支逐轮发现

在空计划首次建模、一次输入显露多个事务方向、新信息引入目标或关系，或既有计划出现明显结构缺口时读取本文。仅需能力介绍时只读 §1.1，不因此进入发现循环。

本文只回答：如何同时管理多个待了解方向，如何一轮一轮追问，以及什么时候才允许展示结构或进入排期。具体 Goal、Todo、Habit 和 TimeConstraint 的语义仍由其他 reference 决定。

## 1. 何时必须进入发现循环

以下任一情况触发发现循环：

- 正式计划为空，用户要求建立或排定近期计划；
- 同一次输入包含多个尚未理解的事务、重复行为或时间竞争，且缺口会改变本次联合安排；
- 新输入可能引入 Goal、Node、归属、依赖、Habit 或 Recurring 结构；
- 已有计划出现结构可疑信号，需要对受影响分支进行修复发现。

已明确对象的纯时间移动、单个用户明确授权的独立 Todo，或不会改变结构的局部事实更新，不必强行进入完整发现循环。

先做局部语义检查不等于必须开启发现循环。已有计划按本次实际缺口和影响范围决定；不因修改了多个已知对象就重做首次访谈。首次建立结构或规划窗口的程序门禁仍保留，但检查可以使用用户已经给出的充分信息，不强制新增提问轮次。

### 1.1 首次开场

是否需要介绍由 [入口的启用规则](../SKILL.md#启用与计划状态) 判断；需要时使用下面的完整介绍：

> 你好，我是你的日程助理，可以帮你照看工作和生活中的各项安排。你可以把事情交给我，我会帮你记住、安排和跟进，情况变化时也会及时调整，让你不用一直惦记和统筹。
>
> 刚开始，你可以简单说说自己的生活习惯，工作和生活中主要有哪些事情，每天几点上班、几点下班，以及最近已经确定的会议、约会或截止时间。
>
> 不需要提前整理，也不用一次说完。你想到什么就说什么，我会帮你归纳，并对真正影响计划的信息逐步追问。

介绍不是新的信息门槛，也不改变本次请求的处理范围。介绍后按入口路由承接已有输入，只有满足 §1 条件才进入发现。问题按本次缺口选择，不把介绍中的类别做成问卷，不扩写内部对象、数据结构或校验流程。

## 2. 先建立发现分支，不立即建模

将用户的第一批输入拆成当前会话中的发现分支。分支表示一个可能需要单独理解的事务方向，不是正式 Goal 或新的持久化模块。

例如“进度会、老板沟通、骑车通勤、周末饭局”至少形成：

- 工作沟通分支；
- 重复骑行分支；
- 社交安排分支；
- 稳定作息和其他近期时间竞争的广度扫描。

每个分支在当前会话中使用以下临时状态：

- `open`：仍有会改变对象类型、结构、关系或近期可行性的问题；
- `ready`：已足以建模，关系检查也已完成；
- `deferred`：已明确暂不纳入，并能说明它为什么不影响当前计划窗口。

用户没有回答某个问题，不得将该分支从 `open` 自动改为 `ready` 或将答案推断为“没有”。

每个 `ready` 分支还必须分别完成：

- `outcome_check`：已能说明该事项最终要产生、推动或维持的结果，或有依据确定它只是不需要 Goal 的独立事项；知道目的不等于必须额外建立结果 Goal，Habit 可直接用自身 outcome 表达；
- `domain_scope_check`：首次整体规划检查同领域并行责任、固定事务及近期后续；增量或明确单项检查本次范围与实际时间竞争，复用已有背景，不要求重复了解完整领域；
- `relationship_check`：已检查它与其他分支、上层 Goal、并行事项的归属和依赖；新增 Goal 的管理范围已明确，不把工作分组直接视为目标范围。
- `object_classification_check`：按任务结构 §2～3 判断推进方式和管理意图，时间事实按时间规则 §1.2 区分安排、禁排限制与作息；不以终点、重复词或有无目标归属定类型。明确检查后不适用时使用 `not_applicable`。

每个分支还维护 `unresolved_questions`。这里只记录仍会改变对象定位、任务结构、任务去留、协作可行性或近期排期的问题；达到 `ready` 或 `deferred` 前必须清空，不能把“已经做过检查”和“没有问题”混为一谈。

例如“准备文档，两小时，会后继续修改”只弄清了部分行动和工作量，并没有回答文档和汇报最终要促成什么决策或交付，也没有说明这是否代表用户当前工作的主要全貌。该工作分支仍是 `open`。

## 3. 逐轮追问循环

每收到一次用户回答，按以下顺序处理：

```text
更新已回答的分支
→ 识别答案是否产生新分支或新的上层目标候选
→ 重新扫描全部 open 分支
→ 选择当前影响最大的一个主要方向
→ 只询问该方向的一组紧密相关问题
→ 等待下一次回答后重复本循环
```

“一次只问一组”只限制单轮的问题广度，不限制首次发现的总轮数。不得因为已经问过一轮就进入排期。

同一轮可以合并询问同一主要方向内的两到三个强关联问题，例如共同结果、会前准备和会后跟进。不要在一轮中同时盘问工作目标、骑行动机、周末空闲和所有生活领域。

### 选择下一分支

在全部 `open` 分支中按以下影响选择下一组问题：

1. 会改变共同目标、任务去留、归属或依赖；
2. 会改变 Habit、Recurring、Todo 或 TimeConstraint 分类；
3. 会产生新行动、新协作条件或新分支；
4. 会改变 DDL、容量或近期日程是否可行；
5. 只影响软排序和体验。

当用户的回答只补齐了当前分支的行动、时长或近期后续，而该分支的 outcome、Goal 边界或同领域责任范围仍未解决时，下一轮继续当前分支。不得为了看起来“已经轮到别的方向”而切到影响更低的分支。

某个分支变为 `ready` 后，必须继续检查其他 `open` 分支，不得因为最紧急的事已经弄清就开始画日历。

## 4. 广度扫描与停止条件

首次整体规划的广度扫描检查以下近期相关内容；它们是回忆与理解提示，不是逐项问卷：

- **事务：**近期工作、学习、健康、家庭、社交和必须处理的生活事项；
- **目的与动机：**希望得到什么、为什么现在做、是主动追求、外部要求还是维持现状，以及是否服务更高结果；
- **行为模式：**作息、通勤、运动、饮食、学习、家庭和社交等稳定节奏；
- **当前现实：**进度、承诺、暂定安排、硬 DDL、协作等待、本周例外和主要时间竞争。

先做广度扫描，再只深入会影响近期结构和排期的分支；不要把领域提示变成要求用户逐项填写的人生问卷。对工作、学习等容易同时存在多个责任的领域，广度扫描不能只问“这个项目还有什么”；还要低成本确认它是否代表用户当前的主要责任，是否还有其他并行项目、例行责任或下一计划窗口已知工作。目标是获得近期计划所需的工作全貌，不是追问完整职业生涯。

在展示首次任务结构方案前，进行一次低成本的明显漏项检查，确认主要事务、行为和时间竞争已基本覆盖。

上述范围由当前请求决定：首次整体规划覆盖主要事务；已有计划的增量或局部修复只覆盖本次相关对象及实际影响。范围外未知问题不填写成已解决，也不强制一并修复。一个联合操作内仍有关键未知时，不先提交其中一部分来绕过停止条件。同条消息中真正独立、已授权的其他更新按 `decision-and-confirmation.md` 第 8.1 节处理，不因此将未解决分支标成 ready 或 deferred，也不拆开首次整体发现。

只有同时满足以下条件，才能结束发现循环：

- 所有当前计划窗口内的分支都是 `ready` 或 `deferred`；
- 每个分支都已检查与其他分支的共同目标、归属和依赖；Linear 和 Recurring 均已按任务结构 §3 检查有验收、交付或依赖意义的近期中间成果，不能默认跳过 Node；
- 广度扫描已完成；
- 没有未解决的重复行为管理意图；
- 没有会改变结构或近期可行性的未解决问题。

持续交付意图已明确、当前工作可处理时，未来频率或模板待定不阻止分支 ready；保留已知事实与待定项，只有请求推导后续各期时才检查循环生成条件。节点检查不要求强造节点，也不要求首次拆完远期结构。

停止依据是分支就绪状态，不是已经追问了几轮。

## 5. 结构提案和排期门禁

发现循环结束后，存在新增业务推导时展示整组结构提案，包括：

- 各主要分支的目的和预期结果；
- 哪些事项被归到同一 Goal，以及依据；
- 必要的 Todo、依赖和重复行为分类，以及相关 Todo 的已知截止或待确认的截止建议（确认规则 §7.1）；
- 安全估算、待确认假设和已暂不纳入的分支。

如果结构包含 Agent 推导的 Goal、Node、Todo 拆分、归属或依赖，用户确认前不得写入正式计划。用户确认后仍要重新读取正式计划，再构造候选。

如果全部业务含义已由用户明确表达，只做字段转换且无其他关键缺口，不为了满足流程再要求一次结构确认；完成所需 scheduling gate 后按原授权处理。

### 发现状态校验

`validate_discovery.py` 检查字段、状态、模式及确认标记的一致性，不读取用户对话，不能证明理解正确或用户确实已确认。先根据对话与正式事实判断就绪，再如实构造状态；校验成功不能补足尚缺的事实或授权。

在展示结构提案前，将当前发现分支写入一次性临时 JSON，设置 `gate = proposal`，运行：

```bash
python3 scripts/validate_discovery.py <temporary-discovery.json>
```

用户确认结构后，重建临时 JSON，将 Agent 推导结构对应分支的 `confirmation` 设为 `confirmed`，将 `gate = scheduling`，再运行一次。

任一次校验失败时，不得构造或提交正式计划候选。临时发现文件不是业务数据，成功或失败后安全删除，不在 workspace 建立长期的第二事实源。

`validate_discovery.py` 的必填结构：

```json
{
  "gate": "proposal",
  "mode": "first_discovery",
  "breadth_scan_complete": true,
  "structural_audit_complete": true,
  "branches": [
    {
      "id": "work-alignment",
      "title": "工作对齐",
      "status": "ready",
      "outcome_check": "complete",
      "domain_scope_check": "complete",
      "relationship_check": "complete",
      "object_classification_check": "complete",
      "unresolved_questions": [],
      "structure_source": "agent_derived",
      "confirmation": "pending",
      "deferred_reason": null
    }
  ]
}
```

`outcome_check`、`domain_scope_check` 和 `object_classification_check` 使用 `pending`、`complete` 或 `not_applicable`。`not_applicable` 必须表示已做过检查并有依据认定不适用，不是“还没问”的替代值。`mode` 使用 `first_discovery`、`incremental_discovery` 或 `repair_discovery`。修复模式还必须完成受影响结构审计。

`structure_source` 按业务含义归因：没有新增或修改正式结构时使用 `none`；用户已经清楚表达业务含义、仅需转换成现有字段时使用 `user_explicit`，不要求用户使用对象术语；至少一项目标、结果、拆分、归属、依赖或管理方式是 Agent 新提出的，整个分支使用 `agent_derived`。具体边界见 `decision-and-confirmation.md` 第 6 节。用户说“是一条线”“帮我排上”不自动确认尚未展示的新增结构。混合分支确认时指出新增理解，不重新审批已经说清的事实。

尤其不要把“用户提供了全部原始事实”当成“用户已指定并确认整组对象结构”。首次多项目归纳、Habit 与交付目标的共享结构、旧独立链的目标归组，只要整组结构是 Agent 组织的，仍走提案与确认；普通明确单项和用户直接指定的具体关系不因此增加确认轮。

确认状态必须与来源和 gate 一致：`none`、`user_explicit` 使用 `not_required`；`agent_derived` 在 proposal gate 使用 `pending`，在 scheduling gate 只有用户已经明确接受展示过的结构时才能使用 `confirmed`。

## 6. 已有坏基线的修复发现

“正式计划已存在”不等于“任务结构已经可靠”。已有计划出现以下任一信号时，对受影响分支进入 `repair_discovery`：

- 存在明显依赖链或同一交付链的多个 Todo，却全部无归属；
- 会议前准备、会议后修改已是 Todo，但会议仍只被视为纯时间占用；
- 重复行为的现有类型与用户管理意图不符，或意图仍不明确；
- 已有周日程包含多个明显相关的行动，却没有能解释它们的 Goal 或已确认的独立理由。

修复发现只调查可疑分支和它影响的近期日程，不重新进行整套首次访谈。修复结构需要取消、移动或替换既有对象时，继续按重大取舍规则取得确认。

`apply_plan.py` 对旧计划中存在依赖且两端 Todo 都无归属的链作局部硬保护：

- 改变相关任务的归属、依赖、状态、余量或执行条件时，要求已完成审计的 `repair_discovery` scheduling state。前置任务的变化向后影响；DDL/窗口还检查其前置约束。Goal/Node 的条件变化通过实际归属路径关联到 Todo。
- 使用旧、新依赖关系判断关联，删除旧边不能隐藏原链；不因共享日期、标题、优先级或同一个上游，就把所有兄弟分支纳入审计。
- 无关任务变化、仅改日程时刻或排名、不改变含义的文字整理，不单独触发修复门禁。时间合法性、授权和其他提交保护照常执行；若实际还改了相关执行条件，则重新判断。
- 候选新增结构仍受首次或增量门禁约束。程序只识别上述可计算信号，会议和重复行为等语义问题仍由 Agent 判断。

修复审计不等于重新询问用户，也不等于必须建立 Goal：已有事实足够时直接完成审计；确实有关键缺口才补问。确认保持独立的任务可以继续无归属。增量/修复 state 的 `breadth_scan_complete` 只指本次范围；其临时自评不能作为后续永久审计证明。

## 7. 语义质量检查

在任何发现模式中，结束前再检查：

- 是否只解决了最紧急的一条，遗漏其他 open 分支；
- 是否将用户未回答的问题当成了否定答案；
- 是否在关系检查前就将事项分类成 TimeConstraint；
- 是否因为用户要求“简单”就跳过了其他方向；
- 是否在用户确认整体结构前写入了由 Agent 推导的任务事实或日程。

该检查不代替结构化发现校验，也不代替正式计划校验。
