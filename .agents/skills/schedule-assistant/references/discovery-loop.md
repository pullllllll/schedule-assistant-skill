# 多分支逐轮发现

在空计划首次建模、一次输入显露多个事务方向、新信息引入目标或关系，或既有计划出现明显结构缺口时读取本文。

本文只回答：如何同时管理多个待了解方向，如何一轮一轮追问，以及什么时候才允许展示结构或进入排期。具体 Goal、Todo、Habit 和 TimeConstraint 的语义仍由其他 reference 决定。

## 1. 何时必须进入发现循环

以下任一情况触发发现循环：

- 正式计划为空，用户要求建立或排定近期计划；
- 同一次输入包含两个或以上可能独立的事务、重复行为或时间竞争；
- 新输入可能引入 Goal、Node、归属、依赖、Habit 或 Recurring 结构；
- 已有计划出现结构可疑信号，需要对受影响分支进行修复发现。

已明确对象的纯时间移动、单个用户明确授权的独立 Todo，或不会改变结构的局部事实更新，不必强行进入完整发现循环。

### 1.1 首次开场

首次空计划发现开始前，先按 `SKILL.md` 的“首次使用预期管理”判断是否需要介绍日程助理。需要时先使用其中的标准文案，再继续处理用户同一条消息中已经给出的事实；介绍本身不创建发现分支，也不要求用户重新提供信息。

首轮问题仍遵循逐轮发现规则：先归纳用户已经说清的内容，再选择当前影响最大的一组缺口询问。不得因为标准文案列举了生活习惯、主要事务、上下班时间、会议、约会和截止时间，就把这些项目一次性做成问卷。当前对话已经介绍过、正式计划已有内容，或请求不准备建立正式计划时，不重复介绍。

## 2. 先建立发现分支，不立即建模

将用户的第一批输入拆成当前会话中的发现分支。分支表示一个可能需要单独理解的事务方向，不是正式 Goal 或新的持久化模块。

例如“进度会、老板沟通、骑车通勤、周末饭局”至少形成：

- 工作沟通分支；
- 重复骑行分支；
- 社交安排分支；
- 稳定作息和其他近期时间竞争的广度扫描。

每个分支在当前会话中使用以下临时状态：

- `open`：仍有会改变对象类型、结构、关系或近期可行性的问题；
- `ready`：已足以建模，关系检查也已完成；
- `deferred`：已明确暂不纳入，并能说明它为什么不影响当前计划窗口。

用户没有回答某个问题，不得将该分支从 `open` 自动改为 `ready` 或将答案推断为“没有”。

每个 `ready` 分支还必须分别完成：

- `outcome_check`：已能说明该事项最终要产生或推动的结果，或有依据确定它只是不需要 Goal 的独立事项；
- `domain_scope_check`：已检查同一领域内的并行责任、固定事务和近期后续，足以判断当前及下一计划窗口的主要时间竞争；
- `relationship_check`：已检查它与其他分支、上层 Goal、并行事项的归属和依赖。
- `object_classification_check`：已区分 Todo、TimeConstraint、Habit、Recurring 或不需要正式对象的背景；明确检查后不适用时使用 `not_applicable`。

每个分支还维护 `unresolved_questions`。这里只记录仍会改变对象定位、任务结构、任务去留、协作可行性或近期排期的问题；达到 `ready` 或 `deferred` 前必须清空，不能把“已经做过检查”和“没有问题”混为一谈。

例如“准备文档，两小时，会后继续修改”只弄清了部分行动和工作量，并没有回答文档和汇报最终要促成什么决策或交付，也没有说明这是否代表用户当前工作的主要全貌。该工作分支仍是 `open`。

## 3. 逐轮追问循环

每收到一次用户回答，按以下顺序处理：

```text
更新已回答的分支
→ 识别答案是否产生新分支或新的上层目标候选
→ 重新扫描全部 open 分支
→ 选择当前影响最大的一个主要方向
→ 只询问该方向的一组紧密相关问题
→ 等待下一次回答后重复本循环
```

“一次只问一组”只限制单轮的问题广度，不限制首次发现的总轮数。不得因为已经问过一轮就进入排期。

同一轮可以合并询问同一主要方向内的两到三个强关联问题，例如共同结果、会前准备和会后跟进。不要在一轮中同时盘问工作目标、骑行动机、周末空闲和所有生活领域。

### 选择下一分支

在全部 `open` 分支中按以下影响选择下一组问题：

1. 会改变共同目标、任务去留、归属或依赖；
2. 会改变 Habit、Recurring、Todo 或 TimeConstraint 分类；
3. 会产生新行动、新协作条件或新分支；
4. 会改变 DDL、容量或近期日程是否可行；
5. 只影响软排序和体验。

当用户的回答只补齐了当前分支的行动、时长或近期后续，而该分支的 outcome、Goal 边界或同领域责任范围仍未解决时，下一轮继续当前分支。不得为了看起来“已经轮到别的方向”而切到影响更低的分支。

某个分支变为 `ready` 后，必须继续检查其他 `open` 分支，不得因为最紧急的事已经弄清就开始画日历。

## 4. 广度扫描与停止条件

广度扫描至少要确认：当前已识别的主要事务、重复行为、稳定作息和近期时间竞争是否已基本覆盖。可以用工作、学习、健康、家庭和生活作为回忆提示，但不得做成领域问卷。

只有同时满足以下条件，才能结束发现循环：

- 所有当前计划窗口内的分支都是 `ready` 或 `deferred`；
- 每个分支都已检查与其他分支的共同目标、归属和依赖；
- 广度扫描已完成；
- 没有未解决的重复行为管理意图；
- 没有会改变结构或近期可行性的未解决问题。

停止依据是分支就绪状态，不是已经追问了几轮。

## 5. 结构提案和排期门禁

发现循环结束后，先展示整组结构提案，包括：

- 各主要分支的目的和预期结果；
- 哪些事项被归到同一 Goal，以及依据；
- 必要的 Todo、依赖和重复行为分类；
- 安全估算、待确认假设和已暂不纳入的分支。

如果结构包含 Agent 推导的 Goal、Node、Todo 拆分、归属或依赖，用户确认前不得写入正式计划。用户确认后仍要重新读取正式计划，再构造候选。

### 确定性就绪校验

在展示结构提案前，将当前发现分支写入一次性临时 JSON，设置 `gate = proposal`，运行：

```bash
python3 scripts/validate_discovery.py <temporary-discovery.json>
```

用户确认结构后，重建临时 JSON，将 Agent 推导结构对应分支的 `confirmation` 设为 `confirmed`，将 `gate = scheduling`，再运行一次。

任一次校验失败时，不得构造或提交正式计划候选。临时发现文件不是业务数据，成功或失败后安全删除，不在 workspace 建立长期的第二事实源。

`validate_discovery.py` 的必填结构：

```json
{
  "gate": "proposal",
  "mode": "first_discovery",
  "breadth_scan_complete": true,
  "structural_audit_complete": true,
  "branches": [
    {
      "id": "work-alignment",
      "title": "工作对齐",
      "status": "ready",
      "outcome_check": "complete",
      "domain_scope_check": "complete",
      "relationship_check": "complete",
      "object_classification_check": "complete",
      "unresolved_questions": [],
      "structure_source": "agent_derived",
      "confirmation": "pending",
      "deferred_reason": null
    }
  ]
}
```

`outcome_check`、`domain_scope_check` 和 `object_classification_check` 使用 `pending`、`complete` 或 `not_applicable`。`not_applicable` 必须表示已做过检查并有依据认定不适用，不是“还没问”的替代值。`mode` 使用 `first_discovery`、`incremental_discovery` 或 `repair_discovery`。修复模式还必须完成受影响结构审计。

`structure_source` 使用保守归因：没有新增或修改正式结构时使用 `none`；Goal、Node、Todo、对象类型、归属和依赖全部由用户直接说清时使用 `user_explicit`；只要其中任一项由 Agent 归纳、拆分、分类或补充，整个分支使用 `agent_derived`。用户说“是一条线”“帮我排上”只确认共同方向和原始请求，不自动确认 Agent 后续补出的对象类型、Todo、归属、依赖或工作量。

确认状态必须与来源和 gate 一致：`none`、`user_explicit` 使用 `not_required`；`agent_derived` 在 proposal gate 使用 `pending`，在 scheduling gate 只有用户已经明确接受展示过的结构时才能使用 `confirmed`。

## 6. 已有坏基线的修复发现

“正式计划已存在”不等于“任务结构已经可靠”。已有计划出现以下任一信号时，对受影响分支进入 `repair_discovery`：

- 存在明显依赖链或同一交付链的多个 Todo，却全部无归属；
- 会议前准备、会议后修改已是 Todo，但会议仍只被视为纯时间占用；
- 重复行为已被建成循环 TimeConstraint，但无法说明用户是否确认不需要追踪；
- 已有周日程包含多个明显相关的行动，却没有能解释它们的 Goal 或已确认的独立理由。

修复发现只调查可疑分支和它影响的近期日程，不重新进行整套首次访谈。修复结构需要取消、移动或替换既有对象时，继续按重大取舍规则取得确认。

`apply_plan.py` 对可确定识别的坏基线加硬保护：若旧计划中两个互相依赖的 Todo 都没有任何 `parent_refs`，修改该任务结构或日程时必须传入已完成结构审计的 `repair_discovery` scheduling state。该门禁不宣称两个 Todo 必须有 Goal；它只强制先审计，然后记录“确实独立”或修复其归属。

## 7. 语义质量检查

在任何发现模式中，结束前再检查：

- 是否只解决了最紧急的一条，遗漏其他 open 分支；
- 是否将用户未回答的问题当成了否定答案；
- 是否在关系检查前就将事项分类成 TimeConstraint；
- 是否因为用户要求“简单”就跳过了其他方向；
- 是否在用户确认整体结构前写入了由 Agent 推导的任务事实或日程。

该检查不代替结构化发现校验，也不代替正式计划校验。
