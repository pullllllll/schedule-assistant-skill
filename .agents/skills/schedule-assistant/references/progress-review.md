# 执行反馈与可信进度恢复

用户报告 Todo 已完成、部分完成、未完成、中断或取消，当前处理依赖尚未确认的过去进度，或准备滚动到新一周时，读取本文。

本文回答：如何以已结束的 Todo ScheduleEntry 确定关注范围，结合用户的自然语言反馈，恢复 Todo 当前可信的状态、剩余工作和必要背景。

本文不把过去的计划时长当成实际投入，不保存逐次执行日志，也不决定恢复进度后哪些未来条目需要重排。

## 主流程

```text
1. 判断当前处理是否依赖未知的过去进度
2. 不依赖时继续原请求；依赖少量 Todo 时局部询问；依赖整体时完整核对
3. 从已结束 Todo ScheduleEntry 确定核对范围
4. 用自然语言理解完成、部分完成、未完成和其他变化
5. 重新估计 Todo 当前剩余工作，并推导相关任务结构状态
6. 将进度结果交给重排和排期流程
7. 局部询问只提交相关事实；完整核对完成后才推进 progress_reviewed_through
```

## 按问题查找

| 当前问题 | 读取章节 |
| --- | --- |
| 这次操作是否需要先问进度 | 1 |
| 应该局部问还是完整核对 | 1 |
| 完整核对包含哪些日程 | 2 |
| 用户没提到的事项能否视为按计划推进 | 3 |
| 完成、部分完成和未完成怎样更新 | 4 |
| 反馈中同时有新任务或时间变化怎么办 | 5 |
| 局部询问和完整核对怎样提交 | 6～7 |
| 很久没使用 Skill 或事后补充反馈 | 8～9 |

## 1. 判断是否需要核对

进度核对不是每次调用 Skill 的固定前置步骤。先处理用户当前请求，只在完成它确实需要未知的过去进度时才询问。

### 1.1 不询问进度

以下情况不因其他未核对历史而阻塞：

- 只读查询；
- 新增或修改一个不依赖过去 Todo 进度的事实；
- 新增会议、不可用时间或其他能独立处理的时间事实；
- 用户主动报告了某个 Todo 的明确当前进度，且本轮只需要处理这个 Todo。

不得因为计划里存在无关的已结束条目，就强制用户先完成整体进度汇报。

### 1.2 局部进度询问

当前处理只依赖少量 Todo 的未知进度时，只询问这些 Todo 的必要信息。例如，为某个已有过去日程的 Todo 新增后续时间时，先问它现在是否已完成、还剩什么和大约还需多久。

局部询问只补足当前处理所需信息，不要顺带遍历所有历史日程。如果影响扩大到大部分 Todo、多个 Goal 间的容量取舍或整体排期，升级为完整进度核对。

### 1.3 完整进度核对

以下情况必须完成完整核对：

- 生成下一段滚动计划或进入新自然周；
- 整体重新编排计划；
- 当前处理依赖核对范围内大部分 Todo 的真实状态。

完整核对不要求用户逐条填写状态，而是先给出大致时间范围和关注对象，让用户自由报告例外，再完成一次“是否还有遗漏”的兜底确认。

## 2. 计算核对范围

### 2.1 ScheduleEntry 与 Todo 的职责

- ScheduleEntry 只表示原计划在某段时间推进某个 Todo，它用来确定核对关注范围。
- Todo 的 `status`、`remaining_estimate_minutes` 和必要的 `context` 才是后续排期使用的当前进度事实。
- ScheduleEntry 结束不会自动完成 Todo，过去的计划分钟数也不会自动从剩余工作量中扣除。

### 2.2 完整核对的确定性范围

完整核对开始时固定一个 `review_cutoff`，通常是本轮计算时刻。待核对 ScheduleEntry 必须同时满足：

```text
source_type = todo
引用的 Todo 存在
ends_at <= review_cutoff
ends_at > progress_reviewed_through
```

`ends_at = progress_reviewed_through` 表示该条目已落入之前的核对范围，不重复询问。正在进行的条目不进入本次范围。

`progress_reviewed_through = null` 只应出现在整份计划尚未建立首周正式日程时。首次建立正式周日程时，将它初始化为该次提交时刻，不为建立计划之前的生活自动制造待核对历史。

### 2.3 同一 Todo 的多个条目

同一 Todo 在范围内可以有多个 ScheduleEntry。将它们按 `todo_id` 聚合，向模型提供相关时间块、Todo 当前状态和剩余工作语义，然后整体判断这一个 Todo。不要逐时间块向用户重复询问，也不要把多个时间块误解成多个 Todo。

以下 Todo 不因本次完整核对自动改变：

- 从未进入具体日程；
- 在核对范围内没有已结束条目；
- 只有未来条目；
- 仅存在于没有具体日程的空窗期，且用户没有主动报告进展。

用户仍可以主动报告这些 Todo 的变化；这属于明确执行反馈，不属于“未提到即按计划推进”。

## 3. 完整核对的交互与兜底基准

完整核对按以下流程进行：

```text
1. 说明本次核对的大致时间范围和关注对象
2. 请用户自由报告未完成、部分完成和其他变化
3. 将自然语言定位到相关 Todo，整理明确例外和预计事实更新
4. 向用户概括当前理解，明确询问是否还有遗漏
5. 用户继续补充时回到第 3 步；明确确认没有遗漏后，再应用兜底基准
```

“用户没提到的已排期事项按原计划推进”只在用户完成最后一步兜底确认后成立。在此之前：

- 不能因为用户暂时没提到某项就认定它已按计划推进；
- 用户不回复时不应用默认结果；
- 本轮完整核对中已提到的进度和其他变化都先作为候选理解，不部分写入正式计划。

兜底确认是对“过去事实是否还有遗漏”的确认，不是对未来重排方案的批准。它完成后，先得到可信进度，再由 `replanning-and-conflicts.md`、`scheduling.md` 和 `decision-and-confirmation.md` 处理未来影响与授权。

## 4. 将用户反馈更新为 Todo 当前事实

用户明确报告的实际结果始终优先于原计划和兜底推断。模型根据 Todo 表达的行动结果、用户语义、相关的过去与未来条目，以及当前剩余工作整体判断。

### 4.1 已完成

- 将 Todo `status` 更新为 `completed`；
- 将 `remaining_estimate_minutes` 更新为 `0`；
- 将该 Todo 尚未开始且已不再需要的未来 ScheduleEntry 列入待移除集合；
- 按 `task-structure.md` 重新推导相关 Node、Linear Goal 和 Habit 当期达标情况。

如果用户在某个 ScheduleEntry 正在进行时报告提前完成，本节先更新 Todo 事实；当前条目尚未发生的剩余时间如何释放，交给 `replanning-and-conflicts.md`。

### 4.2 部分完成或已经开始

- Todo 保持未完成，通常更新为 `in_progress`；
- 用最新 `title` 和必要的 `context` 表达现在还剩什么，不保存流水式进度日志；
- 根据当前剩余行动重新估计 `remaining_estimate_minutes`；
- 后续日程继续引用原 `todo_id`。

只有剩余工作已经变成另一个可独立完成的行动时，才按 `task-structure.md` 拆分或新增 Todo；不得仅因为原定时间已经结束就复制一个新 Todo。

### 4.3 未完成

“这次没做完”本身不能说明 Todo 是 `pending` 还是 `in_progress`：

- 明确未开始时可保持 `pending`；
- 已经开始、尝试或有部分成果时使用 `in_progress`；
- 无论哪种状态，都保留原 Todo 和 `todo_id`，并根据现在仍需要完成的行动重新估计剩余工作量。

未完成不会自动创建替代 Todo。Habit Todo 在周期内优先重排原 Todo；周期结束仍未完成时允许当期不达标，不自动补次数到下一期。

### 4.4 取消、中断和估时变化

- “这次没做”或“中断了”不等于取消 Todo；只有用户表示该行动本身已不再需要时，才按任务结构规则进入 `cancelled`。取消语义明确后，将 `remaining_estimate_minutes` 更新为 `0`，清理不再需要的未来条目，并重新检查上层结果是否仍能成立、需要重新拆解或应被取消。
- 用户只表示需要更多或更少时间时，根据当前剩余工作重新估计，不从原估时上机械加减。
- 不根据已过去的日程分钟数或用户偶尔提到的实际投入时长使用固定公式计算剩余工作量。

### 4.5 兜底的“按计划推进”

完成兜底确认后，未被识别为例外的已排期 Todo 可以以“按原计划推进”为判断基准，但仍不是机械扣减：

- 原计划预期本次投入后即完成，且没有相反反馈时，可以更新为 `completed`；
- 原计划本就包含多次投入或未来仍有必要工作时，保持未完成，结合 Todo 完成语义和当前背景重新估计剩余量；
- 用户明确反馈始终覆盖默认判断。

ScheduleEntry 仍保留原计划时间，不在条目上追加完成状态或实际时长。

## 5. 一条反馈同时包含多种事实

执行反馈可以同时包含 Todo 进度、新任务、Goal/Node 结果变化、DDL、时间占用、可用时间或其他现实变化。不要强迫用户分多轮按数据模块报告。

1. 按本文恢复 Todo 进度；
2. 任务结构事实读取 `task-structure.md`；
3. 时间事实读取 `calendar-and-time-rules.md`；
4. 把全部明确事实合并为同一份候选变更；
5. 由 `replanning-and-conflicts.md` 确定未来影响，再用 `scheduling.md` 排期；
6. 按 `decision-and-confirmation.md` 判断哪些结果已经获得授权。

如果这些反馈属于一次尚未完成兜底确认的完整核对，整份核对候选不部分写入；局部询问或用户主动报告则按当前明确授权形成完整候选并提交。

## 6. 局部询问的提交边界

局部询问取得的明确进度可以正式更新相关 Todo，但不推进全局 `progress_reviewed_through`。

提交前：

1. 基于最新正式计划更新相关 Todo 当前事实；
2. 重新推导相关 Node 和 Linear Goal 状态；
3. 将需要改变的未来日程交给重排和排期流程；
4. 形成完整候选计划，校验并按授权原子提交。

后续完整核对仍从正式 `progress_reviewed_through` 计算全局范围，但必须读取局部询问已经更新的 Todo 当前事实。对同一过去条目不得再次机械扣减剩余工作量，也不得把 Todo 从用户已明确报告的新状态回退。

## 7. 完整核对、确认点与跨周提交

只有完整核对完成兜底确认后，才能将 `progress_reviewed_through` 从原值向后推进到本轮 `review_cutoff`。它不得回退。

一次完整核对产生的：

- Todo 状态、剩余工作和必要背景更新；
- Node、Linear Goal 和 Habit 当期状态的派生更新；
- 未来 Schedule 移除、释放或重排；
- 新的 `progress_reviewed_through`；

必须在同一份完整候选计划中处理。不能先推进确认点，再单独处理 Todo 或 Schedule。

跨周滚动时按以下顺序：

```text
1. 完成截止 review_cutoff 的全部待核对过去进度
2. 在候选计划中更新 Todo 事实和 progress_reviewed_through
3. 根据更新后的任务状态生成新周日程
4. 在同一候选中清理早于上一自然周的条目
5. 完整校验通过后原子提交全部结果
```

用户尚未完成兜底确认时，不得生成新周正式计划，也不得清理旧条目。新周生成、校验或写入失败时，进度结果、确认点、Schedule 更新和历史清理全部不生效，原正式计划保持不变。

## 8. 长时间未使用 Skill

用户间隔一周或更久后回来时：

1. 先核对 `progress_reviewed_through` 之后实际存在的已结束 Todo ScheduleEntry；
2. 再询问没有具体日程的空窗期里是否有额外进展、新任务、日程承诺或其他现实变化；
3. 只对用户明确报告的空窗期事实进行更新；
4. 不把未排期且未被提及的 Todo 自动视为完成；
5. 完成事实同步后，再按任务结构和排期规则生成新周内需要的周期 Todo 和具体日程。

完整核对范围仍从正式确认点开始，不因日历间隔很长就自行跳过历史。成功滚动后，Schedule 只按数据合同保留紧邻新当前周的上一自然周和新当前周。

## 9. 事后补充与核对中断

用户后来补充 `progress_reviewed_through` 以前发生的进展时，将其作为明确执行反馈更新 Todo 当前事实，但：

- 不回退确认点；
- 不补写、移动或伪造过去的 ScheduleEntry；
- 如果新事实影响未来计划，按重排和授权规则形成当前候选变更。

MVP 不持久化尚未完成的进度核对过程：

- 同一对话上下文可以用来继续询问，但它不是正式数据；
- 新对话、上下文丢失或无法可靠判断之前问到哪里时，从正式 `progress_reviewed_through` 重新计算范围并重新询问；
- 用户完成兜底确认前，不将本轮完整核对的局部结果写入正式计划。

不因为需要恢复询问进度而新增 `progress_review`、`interaction_state`、ExecutionRecord 或 ExecutionSession 数据模块。

## 10. 结果交接与不变量

进度恢复后：

- 字段和完整候选数据读取 `plan-data-contract.md`；
- 上层状态、任务去留或行动拆分读取 `task-structure.md`；
- 未来影响集、当前条目剩余时间释放和旧条目处理读取 `replanning-and-conflicts.md`；
- 具体新日程读取 `scheduling.md`；
- 能否直接提交、是否存在未授权连带影响读取 `decision-and-confirmation.md`。

始终保持：

- ScheduleEntry 结束不自动完成 Todo；
- 正在进行条目不进入常规待核对范围；
- 用户明确反馈优先于原计划和默认判断；
- 不用过去的计划分钟数或偶发实际投入按固定公式推导剩余工作量；
- 局部询问不推进全局确认点；
- 默认“按计划推进”必须等用户确认整个核对范围无遗漏后才成立；
- 尚未完成核对的过去条目不得提前清理；
- 过去条目不被新条目覆盖；
- 完整核对结果、确认点和必要的 Schedule 更新作为一份完整候选处理。
