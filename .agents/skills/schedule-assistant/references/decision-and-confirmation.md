# 自主处理、追问与用户确认

任何可能修改正式计划的操作，在决定直接提交、追问信息或等待用户确认时读取本文。只读查询通常不需要读取。

本文只回答：Agent 可以直接做什么，哪些信息必须追问，哪些代价必须先由用户决定。任务应该怎样建模、Todo 怎样排时间、现实变化影响哪些条目，分别由其他 reference 决定。

## 1. 三种处理结果

对一次不可分割的操作，选择以下一种处理结果。同一条消息中的独立更新按第 8.1 节判断，不把消息本身当成必须全部等待的事务边界：

| 结果 | 何时使用 | 该操作能否修改正式计划 |
| --- | --- | --- |
| 最少必要追问 | 缺失信息会改变对象定位、任务结构、容量判断或近期排期 | 否；先取得必要事实 |
| 直接提交 | 用户已经授权原始修改，且完整影响可以在现有硬约束和权限内吸收 | 是；完整校验后原子提交 |
| 展示整组方案 | 存在尚未授权的重大取舍，或无法判断应由谁承担代价 | 否；等待用户选择、修改或拒绝 |

不要把“信息不全”和“需要用户做取舍”混为一谈：前者询问事实，后者展示代价明确的可选方案。

## 2. 判断当前操作

判断一次操作能否推进，需要明确：

- 用户要执行修改，还是只查看、解释或要方案；
- 正式对象、行动结果及关系是否足够清楚；新结构按第 6 章，关键缺口按第 3 章，纯时间调整保持局部；
- 原话授权的动作及限制，以及完整结果的派生影响；普通连带改期按第 5.1 节，不扩大到无关调整或新取舍；
- 完整结果没有关键未知或未授权取舍时，按 [提交操作](plan-write-workflow.md) 处理；否则先补事实或展示整组方案，不先写原始变化再处理后果。独立更新见第 8.1 节。

“帮我看看怎么排”“给我一个方案”只授权建议。“新增”“改成”“取消”“把它排到”等明确执行表达可以授权说清的原始动作及第 5.1 节必要普通连带改期，不自动授权取消、削减其他任务或改变承诺。

“简单排一下”只要求简洁展示。“排上”不能替代行动结果、对象类型、归属、依赖和执行条件；这些含义已清楚时也不为同一动作重复确认。

## 3. 最少必要追问与可见假设

先区分三类信息：已有可信事实直接复用；行动含义明确后可采用低风险、可纠正的估算；不同答案会改变结果、结构或近期可行性的缺口先澄清。用户说“排上”授权执行已经说清的动作，不替代缺失事实。程序接受候选或发现状态，也不证明这些事实已经获得。

**未知不能通过改成独立任务来消除。** 新事项与现有交付、材料或协作方存在明显关联线索时，“用户没有说明归属”不是保持独立的依据；若不同关系会改变前置条件或排期，先澄清再写入。相反，用户明确保持独立，或已有上下文已足以说明它独立可执行且没有关联缺口时，直接复用这一结论，不为每件小事寻找 Goal。

检查就绪时先看尚缺的事实，再决定采用哪种对象：例如“请人处理维修”尚不清楚执行者及协作安排，不能先创建自办 Todo，再用可纠正估时解释这次猜测。最小可行动作也必须是用户授权且确实能执行的动作，不能通过重命名、缩小任务或改变分类绕开原请求的关键未知。

### 3.1 必须追问

只在缺失信息会改变以下结果时追问：

- 用户指的是哪个 Goal、Node、Todo 或 TimeConstraint，且错误定位会影响可执行性或任务去留；
- 多个事项是否共同推进一个结果，或某个行为是否服务尚未确认的上层目标，且不同理解会产生不同结构；
- 重复行为需要助理持续安排和维持，还是仅记录具体安排，且已有表达不足以判断、不同理解会改变安排方式；
- 是否需要建立或重组任务结构；
- 谁执行、对方何时可配合、需要哪些输入，且不同答案会改变任务与占用分类、依赖或能否开展；
- 当前容量是否足够，或近期日程能否合法生成；
- 用户只提供 DDL 日期，没有提供具体时刻；
- 多种理解会产生不同重大取舍。

正式 DDL 必须是用户确认到具体时刻的 datetime。用户只说“周五前”“8 月 30 日截止”时，追问具体时间，不能自行补成当天 18:00、23:59 或其他时刻。

不要给所有新任务固定追加“有截止吗”。已有可靠信息时复用；报名、交付或协作等存在尚不清楚的现实边界且影响当前安排时，才补问。未知截止不等于已确认没有截止。首次整体规划仍需完成相关时间竞争检查；已明确限定且信息充分的单项，不扩大到整个生活领域。

报考、申请等事项即使当前只做比较或准备，外部报名时限仍可能使所选时段过晚。尚无依据时，先低成本核对是否存在这类时限及相关近期安排，再决定排到哪天；用户已明确没有、已有可信背景或请求确实与该现实过程无关时，不重复问。

### 3.2 可以直接假设

低风险且可合理推导的信息不逐字段询问。应采用具体假设继续处理，并在回复中让用户看见、可以纠正。

估时的前提是已理解要做什么及必要执行条件。例如，独立整理一页清单可以在容量允许时暂估半小时；“安装桌板”是谁执行尚不明确时，先排两小时不能代替自装与师傅上门的区分。不要将估算写成用户承诺，也不要用它掩盖归属、依赖、交付或执行者未知。

用户没有提供 Todo `execution_window` 时，可以根据 DDL、依赖、剩余工作量、可用时间和协作条件直接推导并写入。只有窗口选择会改变可执行性或产生重要取舍时，才追问或随任务结构方案确认。

### 3.3 在全部发现分支中选择下一组问题

需要发现时，按 [发现规则 §2～4](discovery-loop.md) 管理相关分支和选择问题。优先解决会改变对象定位、任务去留、共同目标、结构、协作或近期可行性的缺口，软排序与体验随后考虑。明确局部修改复用事实，不因一次提及多项变化重新访谈。

每轮只问一个主要方向的一组强相关问题，同时保留其他未解决分支。用户漏答不等于否定；当前分支的结果或责任范围尚不明确时继续它，不为轮换而切换方向。停止依据是本次相关分支就绪，不是已问过几轮。

### 3.4 用助理式口语自适应引导

追问应使用用户正在使用的日常语言，不要把 Goal、DDL、TimeConstraint 或数据字段名直接变成问卷。能由 Agent 完成的归纳、分类、拆解和估算，不推回给用户。

第一轮先说明当前看到的全部主要事务线和候选关系，让用户知道系统没有遗漏其他方向；然后只问本轮的一个主要方向。后续每轮简短说明哪个方向已弄清、现在继续弄清什么。首次主动发现采用广度扫描与信号驱动深入，不一次性盘问所有生活领域。重复行为按任务结构 §2～3 判断；只有信息不足且影响处理方式时，澄清需要助理持续安排和调整行为，还是仅记录具体安排。已知目的直接保留，不例行再问上层目标或扩展其他行为。

引导强度按需逐步上升：

1. **直接推导**：信息含糊但风险低时，使用最可能的具体理解继续，并让用户看得见、可以纠正。
2. **带着理解确认**：需要确认时，先说明当前的具体理解，再让用户修正，不从空白抽象问题开始。
3. **给出有意义的对照**：多种理解会产生不同高影响结果时，说清差别帮助用户判断，不只问“是哪一种”。
4. **帮助回忆真实场景**：用户不知道怎样回答时，从实际一天、已有承诺、可观察结果或执行场景切入，不只是换一种说法重复原问题。
5. **允许不确定答案**：不需要精确事实时，允许用户先给大概范围，或由 Agent 使用可纠正的临时理解。正式 DDL 时刻等必须精确的硬事实不得因此降级为猜测。

用户已经说清时，不进行多余解释或追加选项。普通事实追问直接问缺失信息；需要解释时，简短说明它会怎样影响安排或跟进，不把事实澄清表述成申请执行许可。具体话术结合当前上下文动态生成，不建立覆盖每种情况的固定话术库。

内部判断与用户沟通分开：对象分类、授权判断、规则检查和提交校验仍完整执行；对外展示具体安排、有意义的取舍、必要假设及需要用户决定的事项。结构方案需要确认时，直接确认方案内容，不例行附上“依据 Skill 规则”的说明、规则原文或文件链接。未完成或受限制时，如实说明结果、实际原因和可行的下一步，不仅用规则引文代替解释；用户询问依据时再提供来源。宿主明确要求的技能使用声明、审批说明和引用仍按其要求执行。这是表达边界，不减少必要追问、结构确认或提交门禁。

普通计划对话中，不主动使用“正式计划框架”“合法候选”“原子提交”“时间事实”“小时级日程”或“校验并提交”等内部流程语言。优先说“我先把这几件事的关系理清楚”“我再确认一下时间没有撞车”等用户能直接理解的结果。

### 3.5 新旧事实冲突

新输入与正式计划或本轮早先事实不同时，先判断是可以并存的补充、用户明确更新，还是仍有歧义的冲突：

- 用户明确更正、改期、取消或更新状态，且对象、作用范围和新含义清楚时，该表达就是相应原始修改的授权。采用新事实并说明结果，不再询问是否覆盖旧值；不要求用户使用固定的更正句式。
- 仅凭信息更晚或描述更具体，不能判定旧事实失效。指代、时间、确定性或影响范围不清，且不同解释会改变安排时，指出具体缺口并澄清；可以同时成立的信息保留各自含义。
- 明确更新只覆盖用户说清的变化。合并后按第 5、6、9 节判断派生结构和连带取舍，不把更正授权扩展到新的业务选择，也不据此改写受保护的过去条目。

例如，“刚才说错了，是周四三点，不是周三”在会议身份和日期清楚时直接采用；“好像改到周四了”仍有影响安排的确定性缺口。

用户只给“晚上前”“这周内”等模糊边界时，可以据此安排更早的行动并说明推导，但不能把它静默写成某个精确正式 DDL。是否必须补问具体时刻，继续按本节对近期合法性和结构影响的判断处理。

## 4. 每周首次排期与新增 Todo

### 4.1 每周第一次建立日程

每个自然周第一次建立该周正式日程时，可以直接生成、校验并提交，不需要先展示日程候选方案。

这项规则只免除“任务结构已确立后，再展示整周具体时间等待确认”，不免除首次或增量语义检查，也不授权把尚未理解的会议、通勤或重复行为直接建成 TimeConstraint。提交前仍必须：

- 按进度核对规则完成本次排期依赖的过去进度恢复；进入新周或生成下一段滚动计划时，完成要求的完整进度核对；
- 获取并解释本次排期需要的日历、可用时间和 TimeConstraint；
- 使用已经确立或已经获得用户确认的任务结构；
- 已检查当前输入中的共同目标、潜在上层目标、重复行为管理意图和明显近期漏项；
- 形成完整候选数据，通过全局校验后再原子提交。

这个直接提交权限只适用于具体日程。如果生成日程前，Agent 还需要自行推导新的 Goal、Node、Todo、候选上层目标、共享归属或依赖，先按第 6 章确认任务结构；结构确认并正式建立后，本周日程仍可直接生成。用户已经明确给出的独立事件、不可用时间或单个独立 Todo，不要求为了首次使用强行创造 Goal。

该周正式日程建立以后，新增、修改和现实变化都按调整逻辑处理：原始修改已获授权，且完整结果没有尚未授权的重大取舍时可以直接提交；涉及其他 Todo 的普通连带改期按第 5.1 节判断，不因移动本身重复确认。

### 4.2 用户明确新增单个 Todo

用户明确要求新增单个 Todo 时，先检查该行动是否已经达到直接提交就绪：

- 行动结束时产生什么结果可以独立判断；
- 对象类型已经明确为 Todo，而不是 TimeConstraint、Habit 或 Recurring；
- 已能可靠定位到已有 Goal/Node，或已明确保持独立；
- 不存在尚未确认的新归属或依赖；
- 不存在会改变任务去留或近期可行性的未解决问题。

全部满足时，才把它视为用户明确新增的单个 Todo。“弄一下申请”“联系一下场地方”“处理一下合同”等含糊表达，在完成结果或对象类型仍有多种合理解释时，不属于可直接提交的单个 Todo。

用户直接说了动作名称，只能证明想做这件事；“联系物业”还没有说明要取得哪种答复，“处理宣传册”还没有说明要形成何种结果。不能自行选择其中一种完成标准后再将整项归为用户明确事实。

- 能使用空闲容量完成，或只需第 5.1 节允许的普通连带改期：直接提交并说明结果。
- 语义未就绪：先进行最少必要追问，正式计划保持不变。
- 需要 Agent 推导归属、依赖或任务拆分：先展示结构方案。
- 完整执行需要尚未授权的重大取舍：展示包含新 Todo 和全部关键连带影响的整组方案，确认前均不写入。
- 当前只能生成建议而用户没有授权执行：只回复建议，不建立 Todo。

## 5. 重大取舍

重大取舍是需要用户决定由什么事项承担代价的变化。当以下变化由系统主动提出，或它们是执行用户原始命令所必需但尚未获得授权的连带影响时，必须事前确认：

- 移动或取消用户承诺、独立事件或其他默认不可移动的 TimeConstraint；
- 新增、修改或放宽正式 DDL；
- 修改计划时区，或改变已有时间事实应保留绝对时刻还是当地钟表时间的解释；
- 取消、放弃、替换任务，或者降低已约定的 Goal/Node 结果；
- 明显增加单日负担，或者突破用户默认可用时间；
- 因完成结果变化而新增、删除、替换或重组下层任务结构；
- 为吸收本次变化而削减其他任务的工作量或必要日程覆盖，或将其移出原执行窗口；
- 无法可靠判断事项相对重要性，系统必须替用户选择牺牲对象。

重大取舍必须等待用户选择、修改或拒绝。Agent 可以解释风险并提出推荐方案，但不能静默替用户选择代价。

如果用户已在当前命令中明确指定上述某个动作，该动作已获授权，不因它属于重大变化而重复询问。对其余连带影响，普通改期按第 5.1 节处理；仍需取消其他事项、削减工作或改变承诺等未授权取舍时，展示整组方案。

以下情况本身不构成重大取舍：

- 符合第 5.1 节的普通 Todo 改期，包括必要的连带移动；
- 在不改变其他正式安排的空闲容量中新增日程；
- 简单修改 Goal 或 Node 的表述，而不改变 outcome 的实质或下层结构；
- 删除条目后运行 `rank_plan.py` 重算剩余关注顺序；即使看似只是连续重编号，也不手工写排名。

原始修改已获授权，且完整结果满足以下普通改期边界、没有其他未授权取舍时，可以校验后原子提交并说明结果。仅仅排得下不代表已经获得授权。

### 5.1 普通连带改期的自主范围

用户已授权执行新增、修改或重排时，为完成该请求而必要移动其他普通 Todo 的尚未开始条目，可以一并处理，无需逐个征求移动许可。完整结果须同时满足：

- 遵守用户明确限定的日期、对象和“不动其他安排”等范围；只纳入实际冲突、容量或依赖影响，按 `replanning-and-conflicts.md` 最小扩圈，不借机整理无关日程。
- 每个被移动 Todo 仍在各自原 `execution_window`、运行时有效窗口和当前 `planning_window` 内，满足已有 DDL、依赖、默认可用时间和 TimeConstraint；不靠修改这些约束或复制旧可用时间例外制造可行。
- 保留任务身份、结果、结构、剩余工作量及所需日程覆盖，不通过减少已有工作的总覆盖量腾出容量；不改写过去条目，也不以此授权移动正在进行的条目。
- 不产生本章所列其他重大取舍，包括明显增加单日负担。无法判断是否满足时，先补充会改变该判断的必要信息。

仅请求建议时仍不写入。新增结构的必要确认、真实进度核对和提交校验继续执行；本节只免除上述普通时间移动的重复确认。涉及可用时间例外时按第 7.3 节处理。

例如，用户要求明天下午新增一小时整理资料，已有阅读可以在其原窗口内顺延一小时，工作量、承诺和其他约束均不变，也没有明显增加单日负担，可以一起调整并告知；若只能取消阅读、将它移出原窗口，或用户已说其他安排不要动，就不能套用此权限直接提交。

## 6. 任务结构与 outcome

### 直接表达与新增业务含义

用户不需要使用 Todo、Goal 等术语。将已经清楚的行动、占用或关系转成现有字段，整理标题、生成 ID、保留已有关系，不构成新的业务提案。例如，用户明确“比较两家机构并整理一页清单”，可以表达为单个行动；用户明确“电话属于开放日，确认人数后才发布报名页”，可以表达该归属与依赖，无需重新确认同一事实。

这一直接表达权限适用于明确单项，或用户已经直接指定要建立的对象及具体关系。首次把一批事项组织为新的多个 Goal、分解步骤、层级或共享归属时，哪些对象构成整组结构仍由 Agent 提议；不能因为各项原始事实已经齐全，就把整组归纳都标为 `user_explicit`。用户要求“组织好并安排”授权开展工作，不自动确认尚未展示的结构选择。结构确认后再排具体时刻，无需再确认整张日程。

如果需要自行增加目标、交付结果、任务拆分、归属、依赖或重复行为管理方式，或在多种真实含义中作选择，则属于新增业务推导。只有“确认场地人数”不能自动推导所属 Goal 和发布前置关系；只有“这几项是一条线”不能确认尚未展示的目标、步骤与工作量。执行者或必要协作条件不清时，先补事实，再形成结构。

### 推导结构的确认

Agent 根据用户事项推导并拆分新的 Goal、Node、Todo、共享归属或依赖时，先用自然语言展示对用户目的的理解、候选结构、归纳依据和会影响用户判断的假设，再取得确认；不要求用户审阅 JSON。确认前不得把部分 Goal、Node 或 Todo 提前写入正式计划。

用户明确要求新增单个 Todo、修改已有 Todo 的清晰事实，或直接指定明确的结构关系，不等同于 Agent 自行提出整套结构拆分；仍按原始授权和完整影响判断能否直接提交。

启用循环规则、把既有试制/首期绑定到周期或重组普通节点时，说明原工作如何保留、哪些后续工作会新增；已有授权和明确事实可复用，不为字段逐项重问。频率未知不影响确认当前结构。模型推导的节点与依赖作为同一结构方案展示，不先写一部分。

修改 Goal 或 Node `outcome` 时：

- 只改变表述且无需重组下层任务：可以直接更新；
- 会新增、删除、替换或重组下层 Node/Todo：形成包含 outcome、任务结构和日程影响的整组方案；
- 方案确认前，不得先修改 outcome、删除旧任务或移动日程。

## 7. DDL、承诺与可用时间例外

### 7.1 正式 DDL

所有非空正式 DDL 都是硬约束，系统不得自主修改。用户可以在明确执行性表达中直接修改 DDL；系统也可以在无解方案中建议新 DDL，但确认前不得写入。

### 7.2 日程承诺

TimeConstraint 的移动、取消或语义改变需要用户明确授权。系统可以围绕承诺移动普通 Todo，但不能为了让方案可行而静默移动承诺本身。

### 7.3 单条 Todo 突破默认可用时间

只有用户对该 Todo 和当前具体时间明确确认后，才能写入 `availability_exception`。这份确认只授权该 ScheduleEntry，不能扩大 AvailabilityRules，也不能授权其他条目使用相同越界时间。

带例外的条目改变具体时间后必须重新判断：

- 新时间回到默认可用范围：删除例外；
- 新时间仍越界：重新取得针对新时间的确认，不能复制旧确认；
- 新时间违反 Todo 窗口、DDL、依赖或 TimeConstraint：例外也不能使其合法。

## 8. 建议结果的边界

建议结果是当前对话中等待用户修改或确认的整组业务方案，不是正式计划，也不是持久化草稿或临时计划版本。

- 可以直接用自然语言说明方案，不要求先写临时文件。
- 复杂方案为了验证可行性可以在内存、工具参数或临时文件中构造结构化候选，但不能把它当成正式状态。
- 需要确认的方案必须同时展示原始修改和关键连带影响，不能让用户只看到其中一半。
- 该整组方案确认前，其中的原始修改、任务删除和派生重排都不得写入正式计划；独立更新按第 8.1 节处理。
- 当前对话中只有最新一次明确展示、仍待确认且可可靠指代的方案可以被“可以”“就这样”等简短确认指代；无法确定所指方案时先澄清。

用户拒绝方案、进入无法可靠续接的新对话或上下文丢失时，放弃未确认方案，不执行其中的变化。后来的简短确认不能自动恢复已拒绝或无法续接的旧方案。

### 8.1 部分接受与独立更新

用户只接受同一组相互依赖的取舍中的一部分时，视为修改方案：合并接受、拒绝和新要求，重算完整结果，不先提交被接受的一半。修改后的完整结果是否还需确认，按第 9 节判断；未明确接受的结构或取舍不能当作已确认。

同条消息中的另一项更新，只有对象与动作明确、已经授权，且不会改变待确认方案的事实前提、依赖、容量或取舍时，才可独立处理。它的执行也不能依赖待确认部分先落地。标题不同或属于不同 Goal 不足以证明独立；无法可靠证明时，不拆开提交。

例如，“方案先别执行，另外把一个无关任务的标题改掉”，在标题修改不改变任务含义或上述前提时可以处理；如果另一更新会占用待确认方案需要的时间，则合并评估。独立更新也必须基于最新正式计划构造完整候选、完成适用的门禁和校验，不夹带待确认变化；成功后说明哪项已生效、哪项仍待决定，后续提案从新版本重算。

首次整体发现中的已清楚分支不能仅因先达到 ready 就拆出写入。完整进度核对及跨周提交仍按 `progress-review.md` 整体处理，不用独立更新例外提前提交其中的进度、确认点或清理结果。

## 9. 确认、修改与重新计算

用户确认、修改方案或同时补充事实时，不直接提交确认前缓存的补丁：

1. 重新读取最新正式计划，确认本轮反馈所指的有效方案；
2. 一起理解用户接受的内容、明确更正、拒绝的部分和新事实，不能先按旧方案提交再处理补充；
3. 基于合并后的输入重算完整结果及实际影响；
4. 检查具体结果是否仍在有效授权范围内，是否存在尚未确认的结构、重大取舍或关键未知；
5. 信息充分且全部变化已获授权或属于第 5.1 节自主范围时，完成适用校验后原子提交并说明变化；有关键未知则补问，有新结构选择或未授权取舍则展示完整方案及新增待决定部分。

这里的业务语义等价指结果仍落实有效授权中的选择和限制，不要求所有日期、时刻或派生字段与旧候选相同：

- 用户本轮已明确修改的事实纳入有效授权，不为同一更正重复确认；模型新增的目标、拆分、归属或依赖仍按第 6 节确认。
- 普通 Todo 时间调整按第 5.1 节处理。正常 `rank_plan.py` 重算不因 `daily_rank` 变化再次审批；用户明确指定的日期、时刻、顺序和“不动其他安排”等限制仍须遵守。用户指定的顺序覆盖继续使用日期级 `ranking_exception`，不改长期优先级。
- 取消或削减工作、改变结果、DDL、承诺或可用时间例外等变化，若尚未获具体授权，仍按第 5～7 节确认。不能用“同一目标”或“仍排得下”替代这些选择。
- 时间戳、存储顺序和无业务影响的派生字段变化不增加确认步骤；正式对象身份仍按数据合同保留。

例如，“方案可以，但下午三点到四点新增一个会”在会议身份和时间信息充分时一起处理；如果只需允许范围内的普通改期，直接落实并说明，如果必须取消另一项工作则展示新取舍。部分接受遵守第 8.1 节，同一整组的未确认内容不提前写入。

## 10. 提交后的说明

自动提交或确认后提交成功时，回复至少让用户知道：

- 正式计划实际修改了什么；
- 本次确认落实了什么选择，或自主完成了哪些有意义的连带调整；涉及重要取舍时说明业务原因，不例行复述直接处理的权限依据；
- 影响了哪些任务和日期；
- Agent 使用了哪些会影响用户理解的可见假设。

不要求固定话术，也不需要逐字段复述 JSON。未确认方案只能说“建议”“准备这样调整”，不得表述成已经生效；提交或校验失败时必须明确说明本次修改没有生效。

## 11. 领域确认规则的路由

本文决定“是否需要确认、当前授权能覆盖到哪里”；对应的领域 reference 决定“具体需要核对哪些事实或选项、确认后如何处理”。不要为了把所有确认话术放在一处，在本文重复各领域的完整业务规则。

| 当前需要确认的内容 | 读取的领域 reference | 该文档负责什么 |
| --- | --- | --- |
| Goal、Node、Todo、Recurring 或 Habit 的结构与运行方式 | `task-structure.md` | 对象类型、中间成果、结构关系，以及循环规则逐步确定和实例绑定 |
| 过去执行情况、是否有遗漏、可信的当前进度 | `progress-review.md` | 局部或完整核对范围、例外报告和兜底确认流程 |
| 日期语义、可用时间、TimeConstraint 的单次或整组修改 | `calendar-and-time-rules.md` | 时间事实如何解释，修改对象和作用范围如何确定 |
| 现实变化后的重排范围、冲突和无解取舍 | `replanning-and-conflicts.md` | 哪些条目受影响、需要重算什么以及可提供哪些取舍方案 |
| 已授权结果要写入哪些 JSON 字段 | `plan-data-contract.md` | 正式数据的字段、引用关系、权威来源和写入要求 |

进度核对中的“是否有遗漏”是对过去事实的确认，不是对未来候选计划的批准。它按 `progress-review.md` 完成后产生可信进度，再由本文判断随后的计划修改能否直接提交；不要把第 8～9 章的候选方案确认流程机械套用到进度核对。
