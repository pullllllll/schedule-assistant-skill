# 自主处理、追问与用户确认

任何可能修改正式计划的操作，在决定直接提交、追问信息或等待用户确认时读取本文。只读查询通常不需要读取。

本文只回答：Agent 可以直接做什么，哪些信息必须追问，哪些代价必须先由用户决定。任务应该怎样建模、Todo 怎样排时间、现实变化影响哪些条目，分别由其他 reference 决定。

## 1. 三种处理结果

对一次可能改变正式计划的请求，只能选择以下一种结果：

| 结果 | 何时使用 | 本轮能否修改正式计划 |
| --- | --- | --- |
| 最少必要追问 | 缺失信息会改变对象定位、任务结构、容量判断或近期排期 | 否；先取得必要事实 |
| 直接提交 | 用户已经授权原始修改，且完整影响可以在现有硬约束和权限内吸收 | 是；完整校验后原子提交 |
| 展示整组方案 | 存在重大取舍、需要改变其他任务，或无法判断应由谁承担代价 | 否；等待用户选择、修改或拒绝 |

不要把“信息不全”和“需要用户做取舍”混为一谈：前者询问事实，后者展示代价明确的可选方案。

## 2. 统一判断顺序

1. 先确认用户是在要求执行修改，还是只要求查看、解释或提供方案。
2. 定位本次涉及的正式对象，并检查用户描述的是目的、行动、重复行为还是纯时间事实；无法可靠定位且误判会产生实质影响时，进行最少必要追问。
3. 检查输入是否显露共同目标、潜在上层目标、新归属或依赖。已有计划中的纯时间调整保持局部，新结构先按第 6 章处理。
4. 确定用户原话直接授权了哪些原始修改，不把这份授权扩展到未提及的其他任务。
5. 在当前正式计划基础上计算原始修改及全部派生影响；不要先写入原始修改再处理后果。
6. 如果完整结果不包含重大取舍，生成完整候选、校验并原子提交。
7. 如果完整结果包含重大取舍，展示整组方案，确认前保持正式计划不变。

用户说“帮我看看怎么排”“给我一个方案”只授权分析和建议，不授权写入。用户用“新增”“改成”“取消”“把它排到”等明确执行性表达时，原话可以授权对应的原始修改，但不自动授权移动、压缩、取消或推迟其他事项。

“简单排一下”“给我简易日程”等表达只要求输出简洁，不授权跳过事务范围、目标动机、对象定位、任务结构或排期就绪检查。

用户的明确执行命令只确认其原话已经表达清楚的原始动作，不自动证明行动结果、对象类型、Goal 归属、依赖和工作量已经明确。“帮我加进去”“给我排上”“弄一下”不能用于跳过语义定位；缺失信息会改变 Todo、TimeConstraint、Habit、Recurring、归属、依赖或任务去留时，先完成最少必要追问。原始动作明确且语义已经就绪时，不为同一动作重复询问“是否确认”。只有完整执行需要引入超出原话授权的连带变化，或系统主动建议一个需要用户承担代价的变化时，才需要另行确认。

## 3. 最少必要追问与可见假设

### 3.1 必须追问

只在缺失信息会改变以下结果时追问：

- 用户指的是哪个 Goal、Node、Todo 或 TimeConstraint，且错误定位会影响可执行性或任务去留；
- 多个事项是否共同推进一个结果，或某个行为是否服务尚未确认的上层目标，且不同理解会产生不同结构；
- 重复行为是只需保护时间，还是需要逐次完成和周期达标，且该选择会改变 TimeConstraint/Habit 建模；
- 是否需要建立或重组任务结构；
- 当前容量是否足够，或近期日程能否合法生成；
- 用户只提供 DDL 日期，没有提供具体时刻；
- 多种理解会产生不同重大取舍。

正式 DDL 必须是用户确认到具体时刻的 datetime。用户只说“周五前”“8 月 30 日截止”时，追问具体时间，不能自行补成当天 18:00、23:59 或其他时刻。

### 3.2 可以直接假设

低风险且可合理推导的信息不逐字段询问。应采用具体假设继续处理，并在回复中让用户看见、可以纠正。

用户没有提供 Todo `execution_window` 时，可以根据 DDL、依赖、剩余工作量、可用时间和协作条件直接推导并写入。只有窗口选择会改变可执行性或产生重要取舍时，才追问或随任务结构方案确认。

### 3.3 在全部发现分支中选择下一组问题

一批输入包含多个事务方向时，先按 `discovery-loop.md` 建立当前会话的发现分支。每轮都在全部仍为 `open` 的分支中选择下一组问题，不只沿着第一个或最紧急的分支一路问到排期。不按 JSON 字段顺序询问，按下列影响从高到低选择：

1. 错误理解会定位到不同对象，或改变任务去留；
2. 错误理解会遗漏共同目标、潜在上层目标或行为动机；
3. 错误理解会建立或重组不同任务结构，包括 Recurring/Habit 的长期运行规则；
4. 缺失信息会改变结果、主要依赖、协作可行性或重大取舍；
5. 缺失信息会改变 DDL、容量结论或近期日程是否合法；
6. 信息只影响软排序或体验质量。

一轮只问当前最影响计划形态的一个主要方向的一组相关问题。同一方向内的强关联问题可以合并，但不要为了减少轮次而把工作结果、重复行为动机、周末时间和其他生活领域一次抛给用户。

用户每次回答后，重新扫描全部分支并选择下一组问题。用户只回答了本轮的一部分时，未回答问题继续保持未解决，不得推断为“没有”。停止依据是全部近期相关分支已达到 `ready` 或 `deferred`，不是已经问过一轮。

当前分支只获得了“做什么、多久、会后还要修改”等行动级信息，但仍无法表达要推动的 Goal outcome，或尚未检查同领域内的并行责任时，下一轮仍该继续该分支。不得把切换方向当成追问有深度的证据。

### 3.4 用助理式口语自适应引导

追问应使用用户正在使用的日常语言，不要把 Goal、DDL、TimeConstraint 或数据字段名直接变成问卷。能由 Agent 完成的归纳、分类、拆解和估算，不推回给用户。

第一轮先说明当前看到的全部主要事务线和候选关系，让用户知道系统没有遗漏其他方向；然后只问本轮的一个主要方向。后续每轮简短说明哪个方向已弄清、现在继续弄清什么。首次主动发现采用广度扫描与信号驱动深入，不一次性盘问所有生活领域；工具性重复行为先区分“只留时间”与“需要坚持和打卡”，确认后再追问上层目的和同目标近期行动。

引导强度按需逐步上升：

1. **直接推导**：信息含糊但风险低时，使用最可能的具体理解继续，并让用户看得见、可以纠正。
2. **带着理解确认**：需要确认时，先说明当前的具体理解，再让用户修正，不从空白抽象问题开始。
3. **给出有意义的对照**：多种理解会产生不同高影响结果时，说清差别帮助用户判断，不只问“是哪一种”。
4. **帮助回忆真实场景**：用户不知道怎样回答时，从实际一天、已有承诺、可观察结果或执行场景切入，不只是换一种说法重复原问题。
5. **允许不确定答案**：不需要精确事实时，允许用户先给大概范围，或由 Agent 使用可纠正的临时理解。正式 DDL 时刻等必须精确的硬事实不得因此降级为猜测。

用户已经说清时，不进行多余解释或追加选项。必须追问时可以简短说明这项信息会影响什么，但不做长篇规则说明。具体话术结合当前上下文动态生成，不建立覆盖每种情况的固定话术库。

普通计划对话中，不主动使用“正式计划框架”“合法候选”“原子提交”“时间事实”“小时级日程”或“校验并提交”等内部流程语言。优先说“我先把这几件事的关系理清楚”“我再确认一下时间没有撞车”等用户能直接理解的结果。

### 3.5 新旧事实冲突

新输入与正式计划或本轮早先事实冲突时，先判断二者是否可以同时成立。冲突会改变可用时间、任务结构、完成结果或正式承诺时，必须指出具体冲突并让用户确认采用哪一种；不得仅以“新信息更晚”或“描述更具体”为由静默覆盖。

用户只给“晚上前”“这周内”等模糊边界时，可以据此安排更早的行动并说明推导，但不能把它静默写成某个精确正式 DDL。是否必须补问具体时刻，继续按本节对近期合法性和结构影响的判断处理。

## 4. 每周首次排期与新增 Todo

### 4.1 每周第一次建立日程

每个自然周第一次建立该周正式日程时，可以直接生成、校验并提交，不需要先展示日程候选方案。

这项规则只免除“任务结构已确立后，再展示整周具体时间等待确认”，不免除首次或增量语义检查，也不授权把尚未理解的会议、通勤或重复行为直接建成 TimeConstraint。提交前仍必须：

- 按进度核对规则完成本次排期依赖的过去进度恢复；进入新周或生成下一段滚动计划时，完成要求的完整进度核对；
- 获取并解释本次排期需要的日历、可用时间和 TimeConstraint；
- 使用已经确立或已经获得用户确认的任务结构；
- 已检查当前输入中的共同目标、潜在上层目标、重复行为管理意图和明显近期漏项；
- 形成完整候选数据，通过全局校验后再原子提交。

这个直接提交权限只适用于具体日程。如果生成日程前，Agent 还需要自行推导新的 Goal、Node、Todo、候选上层目标、共享归属或依赖，先按第 6 章确认任务结构；结构确认并正式建立后，本周日程仍可直接生成。用户已经明确给出的独立事件、不可用时间或单个独立 Todo，不要求为了首次使用强行创造 Goal。

该周正式日程建立以后，新增、修改和现实变化都按调整逻辑处理：完整结果不影响其他任务时可以直接提交；需要改变其他任务或产生重大取舍时先展示方案。

### 4.2 用户明确新增单个 Todo

用户明确要求新增单个 Todo 时，先检查该行动是否已经达到直接提交就绪：

- 行动结束时产生什么结果可以独立判断；
- 对象类型已经明确为 Todo，而不是 TimeConstraint、Habit 或 Recurring；
- 已能可靠定位到已有 Goal/Node，或已明确保持独立；
- 不存在尚未确认的新归属或依赖；
- 不存在会改变任务去留或近期可行性的未解决问题。

全部满足时，才把它视为用户明确新增的单个 Todo。“弄一下申请”“联系一下场地方”“处理一下合同”等含糊表达，在完成结果或对象类型仍有多种合理解释时，不属于可直接提交的单个 Todo。

- 能使用空闲容量完成，且不改变其他任务的正式安排：直接提交并说明结果。
- 语义未就绪：先进行最少必要追问，正式计划保持不变。
- 需要 Agent 推导归属、依赖或任务拆分：先展示结构方案。
- 必须移动、压缩、取消、推迟或以其他方式改变其他任务：展示包含新 Todo 和全部连带影响的整组方案，确认前均不写入。
- 当前只能生成建议而用户没有授权执行：只回复建议，不建立 Todo。

## 5. 重大取舍

重大取舍是需要用户决定由什么事项承担代价的变化。当以下变化由系统主动提出，或它们是执行用户原始命令所必需但尚未获得授权的连带影响时，必须事前确认：

- 移动或取消用户承诺、独立事件或其他默认不可移动的 TimeConstraint；
- 新增、修改或放宽正式 DDL；
- 修改计划时区，或改变已有时间事实应保留绝对时刻还是当地钟表时间的解释；
- 取消、放弃、替换任务，或者降低已约定的 Goal/Node 结果；
- 明显增加单日负担，或者突破用户默认可用时间；
- 因完成结果变化而新增、删除、替换或重组下层任务结构；
- 必须移动、压缩、取消、推迟其他事项才能吸收本次变化；
- 无法可靠判断事项相对重要性，系统必须替用户选择牺牲对象。

重大取舍必须等待用户选择、修改或拒绝。Agent 可以解释风险并提出推荐方案，但不能静默替用户选择代价。

如果用户已在当前命令中明确指定上述某个动作，该动作已获授权，不因它属于重大变化而重复询问。但授权仍只覆盖用户明确指定的对象和变化；如果还必须牺牲、移动或取消其他事项，对超出原命令的部分展示整组方案。

以下情况本身不构成重大取舍：

- 在 Todo 原 `execution_window` 和既有硬约束内移动其 ScheduleEntry；
- 在不改变其他正式安排的空闲容量中新增日程；
- 简单修改 Goal 或 Node 的表述，而不改变 outcome 的实质或下层结构；
- 删除条目后运行 `rank_plan.py` 重算剩余关注顺序；即使看似只是连续重编号，也不手工写排名。

如果在现有 DDL 和其他硬约束内仍存在可执行方案，可以原子提交日程调整并向用户说明，不需要为了“有变化”本身再次确认。

## 6. 任务结构与 outcome

Agent 根据用户事项推导并拆分新的 Goal、Node、Todo、共享归属或依赖时，先用自然语言展示对用户目的的理解、候选结构、归纳依据和会影响用户判断的假设，再取得确认；不要求用户审阅 JSON。确认前不得把部分 Goal、Node 或 Todo 提前写入正式计划。

用户明确要求新增单个 Todo、修改已有 Todo 的清晰事实，或直接指定明确的结构关系，不等同于 Agent 自行提出整套结构拆分；仍按原始授权和完整影响判断能否直接提交。

修改 Goal 或 Node `outcome` 时：

- 只改变表述且无需重组下层任务：可以直接更新；
- 会新增、删除、替换或重组下层 Node/Todo：形成包含 outcome、任务结构和日程影响的整组方案；
- 方案确认前，不得先修改 outcome、删除旧任务或移动日程。

## 7. DDL、承诺与可用时间例外

### 7.1 正式 DDL

所有非空正式 DDL 都是硬约束，系统不得自主修改。用户可以在明确执行性表达中直接修改 DDL；系统也可以在无解方案中建议新 DDL，但确认前不得写入。

### 7.2 日程承诺

TimeConstraint 的移动、取消或语义改变需要用户明确授权。系统可以围绕承诺移动普通 Todo，但不能为了让方案可行而静默移动承诺本身。

### 7.3 单条 Todo 突破默认可用时间

只有用户对该 Todo 和当前具体时间明确确认后，才能写入 `availability_exception`。这份确认只授权该 ScheduleEntry，不能扩大 AvailabilityRules，也不能授权其他条目使用相同越界时间。

带例外的条目改变具体时间后必须重新判断：

- 新时间回到默认可用范围：删除例外；
- 新时间仍越界：重新取得针对新时间的确认，不能复制旧确认；
- 新时间违反 Todo 窗口、DDL、依赖或 TimeConstraint：例外也不能使其合法。

## 8. 建议结果的边界

建议结果是当前对话中等待用户修改或确认的整组业务方案，不是正式计划，也不是持久化草稿或临时计划版本。

- 可以直接用自然语言说明方案，不要求先写临时文件。
- 复杂方案为了验证可行性可以在内存、工具参数或临时文件中构造结构化候选，但不能把它当成正式状态。
- 需要确认的方案必须同时展示原始修改和关键连带影响，不能让用户只看到其中一半。
- 确认前，原始修改、任务删除和派生重排都不得写入正式计划。
- 当前对话中只有最新一次明确展示的方案可以被“可以”“就这样”等简短确认指代。

用户拒绝方案、进入无法可靠续接的新对话或上下文丢失时，放弃未确认方案，正式计划保持不变。

## 9. 确认、修改与重新计算

用户确认后，不直接提交确认前缓存的补丁：

1. 重新读取最新正式计划；
2. 合并用户本轮确认、修改和同时补充的新事实；
3. 重新计算完整结构化候选及派生影响；
4. 判断新结果与用户刚确认的方案是否业务语义等价；
5. 等价时校验并原子提交；不等价时展示变化后的新方案并再次确认。

业务语义等价不要求 JSON 字节相同。内部 ID、时间戳、对象存储顺序或无用户可见影响的派生字段可以不同。以下变化不等价，必须重新确认：

- 任务结构、任务去留或完成结果发生变化；
- DDL、承诺、Todo 的具体日期或时间发生变化；
- 工作量、用户负担、主要取舍或此前展示的影响范围发生变化；
- `daily_rank` 的改变会改变用户看到的当日关注顺序；用户主动指定的覆盖必须保存日期级 `ranking_exception`，不得改写 Goal 长期优先级。

用户修改方案或补充新事实时，把它们作为新的完整输入重新计算。用户只接受方案的一部分时，视为修改方案，不进行部分提交。一条消息同时包含“确认旧方案”和新事实时，也必须合并后基于最新正式计划重新计算。

## 10. 提交后的说明

自动提交或确认后提交成功时，回复至少让用户知道：

- 正式计划实际修改了什么；
- 为什么可以直接处理，或者本次确认落实了什么选择；
- 影响了哪些任务和日期；
- Agent 使用了哪些会影响用户理解的可见假设。

不要求固定话术，也不需要逐字段复述 JSON。未确认方案只能说“建议”“准备这样调整”，不得表述成已经生效；提交或校验失败时必须明确说明本次修改没有生效。

## 11. 领域确认规则的路由

本文决定“是否需要确认、当前授权能覆盖到哪里”；对应的领域 reference 决定“具体需要核对哪些事实或选项、确认后如何处理”。不要为了把所有确认话术放在一处，在本文重复各领域的完整业务规则。

| 当前需要确认的内容 | 读取的领域 reference | 该文档负责什么 |
| --- | --- | --- |
| Goal、Node、Todo、Recurring 或 Habit 的结构与运行方式 | `task-structure.md` | 对象类型、结构关系、周期、首次开始和稳定模板等具体确认项 |
| 过去执行情况、是否有遗漏、可信的当前进度 | `progress-review.md` | 局部或完整核对范围、例外报告和兜底确认流程 |
| 日期语义、可用时间、TimeConstraint 的单次或整组修改 | `calendar-and-time-rules.md` | 时间事实如何解释，修改对象和作用范围如何确定 |
| 现实变化后的重排范围、冲突和无解取舍 | `replanning-and-conflicts.md` | 哪些条目受影响、需要重算什么以及可提供哪些取舍方案 |
| 已授权结果要写入哪些 JSON 字段 | `plan-data-contract.md` | 正式数据的字段、引用关系、权威来源和写入要求 |

进度核对中的“是否有遗漏”是对过去事实的确认，不是对未来候选计划的批准。它按 `progress-review.md` 完成后产生可信进度，再由本文判断随后的计划修改能否直接提交；不要把第 8～9 章的候选方案确认流程机械套用到进度核对。
