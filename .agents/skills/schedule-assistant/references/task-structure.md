# 任务结构与生命周期

在需要理解用户事务、创建或修改 Goal/Node/Todo、判断归属和依赖、处理 Recurring/Habit，或更新任务生命周期时读取本文。

本文只回答：用户的事务应形成什么任务结构，以及这个结构如何运行和变化。

不要用本文决定 JSON 的完整字段格式、Todo 的具体排期、过去实际完成了多少、现实变化后的重排范围或一项修改是否需要确认。遇到这些问题时，分别读取数据合同、排期、进度核对、重新编排或确认权限 reference。

## 1. 核心对象

### Goal

Goal 是系统持续维护的一项预期结果或持续状态，也是任务结构的最高层单位。

Goal 描述“最终要得到什么”或“长期要维持什么”，不描述具体执行步骤和具体时间块。Goal 或 Node 的完成结果由各自的 `outcome` 表达；Todo 只表达实现结果所需的行动，不另建完成标准。

每个 Goal 创建时都需要在 `P0`、`P1`、`P2` 中选择长期优先级。Agent 可以建议，用户可以纠正。它只表示 Goal 之间的长期相对重要性，不等于本周或今日的直接执行顺序。

### Node

Node 是 Goal 推进过程中具有阶段、依赖或验收意义的中间结果。

只在确实存在阶段边界、中间交付、依赖关系或需要单独判断的结果时建立 Node。不要为了让结构整齐而给每组 Todo 强行增加一层 Node。

### Todo

Todo 是可以直接开始，并能独立判断是否完成的行动。它是进入具体日程的最小行动单位，但不是具体时间块。

Todo 应尽量拆到一次可以独立完成。只有以下情况才让同一个 Todo 对应多段计划投入：

- 初始估时不足，需要继续完成同一个行动；
- 行动无法再按语义合理拆分；
- 行动本身允许分段执行。

到达某个时间、ScheduleEntry 开始或结束，都不会自动改变 Todo 的业务状态。Todo 是否完成来自用户反馈或可信的进度核对。

## 2. Goal 的三种运行方式

正式 Goal 只有三种运行方式：

- `linear`：朝一个明确终点推进，完成后结束。
- `recurring`：按照周期重复产出一轮结果，每轮包含相对稳定的结构。
- `habit`：持续满足每个考核周期的频率或最低次数，不以单次交付结束。

`mixed` 只能用于理解输入时提示“这件事包含多种运行方式”，不是正式 Goal 类型。遇到 mixed 输入时，拆成多个语义相关、但独立运行的 Goal；v0 不引入 Workstream 或更高层项目关系。

独立事件和纯不可用时间不是 Goal。它们可能属于 TimeConstraint；具体边界读取时间规则。

## 3. 从用户输入建立结构

### 先定位，再创建

用户输入是了解现实的线索，不默认是完整计划。处理任何新输入时，先理解用户想得到什么、为什么现在做、它和其他事项是什么关系，再决定正式对象；不得因为输入中出现日期、时刻、会议或重复频率就直接跳到时间分类。

处理新输入时，先结合当前对话和正式计划判断它是：

- 对已有 Goal、Node 或 Todo 的补充或修改；
- 一个新的 Goal；
- 一个暂时没有上层归属的独立 Todo；
- 可能属于 TimeConstraint 的时间事实；
- 只作为背景，不需要建立正式对象的信息。

解析“它”“那个任务”“明天的安排”等指代时，同时使用当前对话和正式计划。无法可靠定位且错误定位会改变任务去留或计划可执行性时，不要猜测；按确认权限规则进行最少必要追问。

### 首次主动发现与后续局部发现

正式计划为空时，先广后深地建立近期规划需要的用户现状图。允许 Goal、零散 Todo、时间事实、重复行为和背景混合输入；用户第一批说出的内容只是入口，不是完整清单。先归纳主要分支，再按信号深入以下四层：

同一批输入存在多个事务方向时，必须同时保留这些发现分支，按 `discovery-loop.md` 一轮一轮深入。用户回答了工作分支，不代表骑行、社交或其他分支已经可建模；用户未回答某个问题，不得将答案推导为“没有”。

- **事务：**近期工作、学习、健康、家庭、社交和必须处理的生活事项；
- **目的与动机：**希望得到什么、为什么现在做、是主动追求、外部要求还是维持现状，以及是否服务更高结果；
- **行为模式：**作息、通勤、运动、饮食、学习、家庭和社交等稳定节奏；
- **当前现实：**进度、承诺、暂定安排、硬 DDL、协作等待、本周例外和主要时间竞争。

先做广度扫描，再只深入会影响近期结构和排期的分支；不要把领域提示变成要求用户逐项填写的人生问卷。对工作、学习等容易同时存在多个责任的领域，广度扫描不能只问“这个项目还有什么”；还要低成本确认它是否代表用户当前的主要责任，是否还有其他并行项目、例行责任或下一计划窗口已知工作。目标是获得近期计划所需的工作全貌，不是追问完整职业生涯。

在展示首次任务结构方案前，进行一次低成本的明显漏项检查，确认主要事务、行为和时间竞争已基本覆盖。

正式计划已存在时，默认只处理用户本次输入涉及的对象和影响范围，但仍需完成增量语义检查：它属于哪个已有对象，是纯时间或状态变化，还是新增行动、结果、归属、依赖或稳定行为。复用已建立的目标、动机和时间基线，不重新要求用户倾倒全部事务；只有新信息无法可靠定位、引入新结构、显露新的上层目标或派生影响扩大时，才局部扩大收集。

已有计划只说明事实已被提交，不自动证明其语义结构可靠。发现相关 Todo 全部无归属、会议准备与修改已建立但会议仍是纯占用，或重复行为无确认意图等信号时，对受影响分支进行修复发现，不继续将新 Todo 追加为独立对象。

### 强制检查向上归纳，不强制建立 Goal

用户先给出清晰结果时，从 Goal 向下识别必要 Node 和近期可执行 Todo。

用户先给出零散行动时，必须检查它们是否共同推进一个已有或可合理归纳的结果。以下任一信号都应触发检查：

- 时间相邻，或用户用“然后、接着、之后、到时候”等方式连接；
- 涉及同一项目、材料、交付或协作链；
- 后一事项可能依赖前一事项的结果；
- 参与者存在汇报、审批或决策关系；
- 多个行为可能服务同一健康、学习、工作或生活结果。

检查可以得到三种结果：明显相关时提出候选共同 Goal；可能相关但信息不足时，带着候选理解追问；确实独立时保留为独立 Todo 或交给时间规则分类。强制的是完成检查，不是一定创建上层对象。

不得为了结构完整而虚构 Goal。后续识别出真实归属时，在原 Todo 上补充归属，保留其身份、状态以及已有日程关系。

### 会议、评审、汇报与沟通

开会、对进度、汇报、评审、过材料、和老板沟通或复盘既可能是目标路径中的行动，也可能只是独立占用。固定时间本身不能决定对象类型。遇到这类输入时，至少检查：

- 它推进什么结果；
- 会前需要准备什么；
- 会中需要确认、决定或交付什么；
- 会后是否可能产生修改或跟进；
- 它与前后会议是否属于同一目标路径；
- 所有这些交付和沟通最终希望促成什么业务结果、决策、验收或状态变化；
- 这条工作线之外，当前及下一计划窗口是否还有其他会争夺时间的项目或例行责任。

如果会议推进目标且结果需要跟踪，将它作为 Todo，并可在 Schedule 中放到固定时间；如果只需保护一个独立外部事件的占用，交给时间规则作为 `commitment` TimeConstraint。不同解释会改变任务结构时先追问，不能只录入会议时段。

### 工具性重复行为与潜在目标

重复出现不自动等于 Habit。用户提到“每天、每周、坚持、连续一个月、最近都要”等行为，且它既稳定占用时间又可能产生健康、学习、社交或职业收益时，依次判断：

1. 它首先是现实义务，还是用户主动维持的行为；
2. 用户是否希望逐次跟踪完成，并判断周期是否达标；
3. 它是否同时服务一个更高层结果。

只需保护时间且不关心完成追踪时，交给时间规则建立循环 TimeConstraint；需要逐次完成和周期达标时建立 Habit Goal 与 Habit Todo；每周期重复交付结果时建立 Recurring Goal。行为具有潜在收益不自动使其成为 Habit，用户的维持和追踪意图才是关键。

例如骑车通勤可能只是交通占用，也可能是需要打卡的骑行习惯，并同时推进减重这一 Linear Goal。先用一问区分占用与习惯；确认习惯后再询问上层目的；确认上层目标后，只做一次同目标的近期明显漏项检查，例如是否同时存在饮食、称重或其他训练。不得未经确认创建这些目标或 Todo，也不得一次性把所有潜在生活方式做成问卷。

同一次行为使用 Habit Todo 表达后，其 ScheduleEntry 已经占用时间，不再复制为 TimeConstraint。共享归属规则见第 4 章，具体时间对象边界读取 `calendar-and-time-rules.md`。

### 控制首次建模深度

首次输入即使很短，也先弄清事项含义、预期结果和会改变近期行动的必要时间信息，不要擅自建立过大的任务结构。

可以提出为近期推进所必需的后续候选 Node，也可以在发现上层目标后检查明显缺失的近期行动，但不要一次性拆解与近期执行无关的远期细节。Goal 没有正式 DDL 时仍可建立结构，并创建“诊断问题、确认时间、收集信息”等真实近期行动；不能伪造完整倒排计划。

### 何时停止收集并展示结构方案

同时满足以下条件时，停止继续追问任务背景，展示当前整组任务结构方案：

- 每个新 Goal 都已能明确表达预期结果；
- 工作、学习等多责任领域已完成当前及下一计划窗口的责任范围检查，不把用户最先提到的一个项目当成全部工作；
- 主要事务的目的和动机已足以解释当前结构；
- 无上层对象的独立 Todo 已经可以直接开始并独立判断完成，不需要为了结构强行追问一个上层 Goal；
- Recurring/Habit 已有足以形成周期、锚点、模板或最低次数方案的信息；
- 重复行为已经区分时间占用、Habit、Recurring 或其他目标手段；
- 明显相关的零散事项已经做过向上归纳，当前范围已完成一次主要事务、行为和时间竞争的漏项检查；
- 同一批输入产生的全部近期相关发现分支都已可建模或明确暂不纳入，不存在“只解决了第一个方向”的情况；
- 会改变近期结构的真实进度和硬 DDL 不再存在高影响歧义；
- Agent 已能推导为近期推进所必需的 Node、Todo、主要依赖和工作量假设。

达到这个门槛后，工作量、执行模式、弹性时间窗和优先级等低风险推导应组成整体方案让用户纠正，不再拆成逐字段追问。Agent 应能说明仍有哪些未知领域以及为什么它们暂不影响本周；与近期执行无关的远期细节，等真正进入近期计划时再补充。方案是否可以写入正式计划，继续按 `decision-and-confirmation.md` 处理。

## 4. 归属、共享和依赖

任务结构不是严格树。一个 Todo 可以没有上层归属，也可以同时推进多条 Goal/Node 路径。

### 独立 Todo

没有 Goal 或 Node 归属的行动是独立 Todo。独立不等于临时、低优先级或不重要，也不要求系统随后必须为它补一个 Goal。

### 共享 Todo

当同一个行动同时推进多个 Goal 或 Node 时，只建立一个共享 Todo，并保存多个有效归属。完成一次即可推进全部有效路径；不得因为归属数量增加而复制 Todo、工作量或同一次计划投入。

Habit Todo 也可以同时服务 Habit Goal 和另一条普通 Goal/Node 路径。例如一次骑行既计入骑行习惯周期，也推进减重目标；保留一个 Todo 和一次计划投入，通过多个 `parent_refs` 表达两个作用。具体字段合法性读取数据合同。

### 修改归属

- 解除一条归属时，只移除对应关系；仍有其他归属时，不改变 Todo 状态。
- 删除最后一条归属但行动仍需执行时，将它保留为独立 Todo。
- 只有行动本身不再需要时才取消 Todo。
- 最后一条归属被移除且行动是否仍需执行不明确时，必须追问，不能把“解除归属”自动解释成“取消行动”。

### 依赖

依赖只表达“必须先完成什么，后续行动才可开始或成立”，不要把一般相关性、推荐顺序或同一 Goal 下的并列关系写成依赖。

Node 可以依赖前置 Node，Todo 可以依赖前置 Todo。共享 Todo 的依赖和完成结果同时作用于它的全部有效归属路径。依赖如何改变有效可排窗口和传播重排影响，读取时间规则与重新编排规则。

## 5. 通用生命周期

### 对象保留与有效归属路径

“对象仍保留在正式计划中”和“对象当前参与排期”不是同一件事。完成、暂停或取消不会自动删除 Goal、Node、Todo 及其已有事实。

对共享 Todo 而言，一条归属路径只有在以下条件同时成立时，才是当前排期使用的有效路径：

- Goal 处于 active；
- 如果路径包含 Node，Node 尚未完成或取消。

暂停、完成或取消的路径暂不贡献当前排期使用的 Goal 优先级和上层 DDL，但原始归属和历史事实继续保留。共享 Todo 只要仍有其他有效路径就继续运行；如果全部非空归属路径都失效，则保留 Todo，但暂不排期。独立 Todo 不依赖上层路径，按自身状态处理。

### 完成

- Linear Goal：全部必要 Node 和直接 Todo 完成后，自动完成。
- Node：至少存在一个有效 Todo，且全部有效 Todo 完成后，自动完成。
- 没有任何有效 Todo 的 Node 不得自动判为完成；应判断它需要重新拆解还是已经不再需要。
- Node 下的 Todo 默认都是必要行动。取消其中一个 Todo 表示该行动不再必要，此时重新检查 Node 是否仍可成立、需要重新拆解或应被取消。

v0 不支持为 Node 定义另一套独立完成公式。

### 暂停与恢复

暂停 Goal 时：

- 保留 Goal 及其既有任务事实；
- 停止生成新的周期实例；
- 只移除由该 Goal 单独驱动的未来日程；
- 共享 Todo 如果仍有其他有效路径，不随该 Goal 一起停止。

恢复 Goal 时，只继续处理尚未结束的当前周期以及本周规划窗口内随后进入范围的周期，不补已经结束的暂停周期。周期实例按原稳定身份复用，不重复生成。

恢复 Linear Goal 时，重新启用原有未完成 Node 和 Todo，使其重新进入待排判断；不要因为恢复而复制任务结构。

### 取消与永久停止

取消 Goal 时，只服务该 Goal 的未完成 Node 和 Todo 一并取消；共享 Todo 仍有其他有效路径时继续保留。

只有用户明确取消某个阶段，或经确认的任务结构调整认定该阶段不再需要时，才取消 Node。取消 Node 时，只服务该 Node 的未完成 Todo 一并取消；共享 Todo 只解除这条 Node 归属，仍有其他有效归属时继续保留。

Recurring 和 Habit Goal 永久停止时进入取消状态，而不是完成状态。停止后不再生成新周期，但保留循环规则、模板、习惯规则、已经形成的历史事实和既有周期身份。

## 6. 修改与纠正

用户补充信息、纠正理解或改变归属时，优先修改原对象，不要因为描述变化就复制 Goal、Node 或 Todo。

修改 Goal 或 Node 的 `outcome` 时：

- 如果只是更准确地描述同一结果，且不影响下层结构，可以保留现有 Node、Todo 和关系。
- 如果结果变化导致行动新增、删除、替换或重组，应形成整组结构变更，并由确认权限规则判断是否可以提交。

只有行动语义已经变成另一件可以独立完成的事时，才拆成新的 Todo。对象被取消不等于从正式计划中抹除；保留它已有的身份和历史事实，未来日程如何清理由进度或重新编排流程决定。

## 7. Linear Goal

Linear Goal 有明确终点。按完成结果识别必要阶段和行动，保持结构足以支持近期执行即可。

## 8. Recurring Goal

Recurring Goal 按周期重复产出一轮结果。每个周期生成一个 Node，并由该 Node 承载本轮 Todo。

完成某一周期只表示该周期结果完成；Recurring Goal 本身继续保持 active，不自动进入 completed 或 paused。

### 建立循环规则

首次建立 Recurring Goal 时，必须明确并确认：

- 周期间隔和单位；
- 首轮开始日期；
- 首轮精确 DDL；
- 每轮稳定复用的 Node/Todo 模板。

后续周期必须从首轮锚点直接计算，不能从上一轮逐次累加，避免日期漂移。月周期按日历月计算；目标月份没有锚点日时使用当月最后一天，但下一周期仍从原始首轮锚点推导。

### 模板与周期实例

循环模板表达每轮固定的 Node 和 Todo 定义。周期实例是当前某一周期真正生成的 Node 和 Todo；是否已经进入具体日程是另一项派生事实。

只有处于 active 状态的 Recurring Goal，才能在新周期进入当前周规划范围时生成实例。同一周期内重排不触发新一轮生成。

每个周期的 Node 与全部 Todo 必须根据模板一次性生成：要么全部成功，要么全部不生效。重复运行时复用同一周期实例，不重复创建整轮结构。

只生成与当前自然周 `planning_window` 相交的正式周期实例，不提前生成以后各周。周期跨越周边界时只生成一次，并在下一周继续复用；远期内容继续由模板表达。

### 修改当前周期或永久规则

- 只修改当前周期时，修改本周期实例，不改变循环模板。
- 用户明确要求“以后每轮都这样”时，才修改模板。
- 模板修改默认只影响尚未生成的周期。
- 如果确实要同步修改已经生成的周期，需要单独展示其具体影响，并按确认权限规则处理。

## 9. Habit Goal

Habit Goal 持续维护每个考核周期的最低完成次数，不生成 Node。每次实际执行机会由独立的 Habit Todo 表达。

### 周期生成

只有 active 的 Habit Goal 才生成周期 Todo；同一周期内的重排不得触发新一批生成。

每个周期默认只生成 `minimum_count` 个 Todo，不自动生成备用次数。只生成当前自然周规划窗口需要的正式 Habit Todo，不提前生成以后各周；跨周周期继续复用已经生成的同一批实例。

`session_minutes` 只用于生成 Habit Todo 的初始估时。后续调整某个 Todo 的剩余估时，不得反向修改整个 Habit 的默认单次时长。

### 长期偏好与本期窗口

Habit 专属、需要跨周期复用的偏好星期和偏好时段属于 Habit 长期规则：

- 默认作为软偏好，排期应尽量满足，但不满足不代表计划非法；
- 用户明确表达“只能”“必须”等要求时，才作为硬约束；
- 只影响当前周期的临时变化写在本期 Todo 的可执行窗口中；
- 用户明确表示“以后都这样”时，才修改长期规则；
- 用户对所有任务普遍适用的作息仍属于 AvailabilityRules，不要写成某个 Habit 的专属偏好。

具体字段由数据合同定义，软硬偏好如何选择时间由排期规则定义。

### 增加、未完成和达标

- 用户要求本周期额外增加一次时，创建下一次 Habit Todo，但不自动提高以后周期的 `minimum_count`。
- 只有用户明确修改长期最低标准时，才更新以后周期的 `minimum_count`。
- Habit Todo 未完成时，优先重新编排原 Todo，不创建替代 Todo。
- 周期结束仍未完成时，允许该周期不达标，不自动补次数到下个周期。
- 本周期已完成次数达到 `minimum_count` 即视为本周期达标；Goal 本身仍保持 active，不因一次达标而完成或暂停。
