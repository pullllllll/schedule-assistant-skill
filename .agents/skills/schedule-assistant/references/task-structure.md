# 任务结构与生命周期

在需要理解用户事务、创建或修改 Goal/Node/Todo、判断归属和依赖、处理 Recurring/Habit，或更新任务生命周期时读取本文。

本文只回答：用户的事务应形成什么任务结构，以及这个结构如何运行和变化。

不要用本文决定 JSON 的完整字段格式、Todo 的具体排期、过去实际完成了多少、现实变化后的重排范围或一项修改是否需要确认。遇到这些问题时，分别读取数据合同、排期、进度核对、重新编排或确认权限 reference。

## 1. 核心对象

### Goal

Goal 是系统持续维护的一项预期结果或持续状态，也是任务结构的最高层单位。

Goal 描述“最终要得到什么”或“长期要维持什么”，不描述具体执行步骤和具体时间块。Goal 的期望结果与 Node 的交付结果由各自的 `outcome` 表达；Habit 的目的与周期达标分开判断，见 §9。Todo 只表达实现结果所需的行动，不另建完成标准。

每个 Goal 创建时都需要在 `P0`、`P1`、`P2` 中选择长期优先级。Agent 可以建议，用户可以纠正。它只表示 Goal 之间的长期相对重要性，不等于本周或今日的直接执行顺序。

### Node

Node 是 Goal 推进过程中可以独立判断的成果，组织相关行动并承接验收和依赖。`regular` 表示普通成果节点；`cycle` 表示某一期重复交付，只有 Recurring Goal 使用。Linear 和 Recurring 都需要识别有意义的 Node；普通节点可以出现在准备、推进或运营的任何时期。

有独立成果、验收意义或前后依赖的行动组应归纳为 Node，不默认把复杂目标扁平化成一串 Todo。简单目标或单个行动可以直接挂 Goal；不以数量、活动分类或时间分段强制加节点。结构保持 Goal → Node → Todo，不嵌套 Node。

### Todo

Todo 是可以直接开始，并能独立判断是否完成的行动。它是进入具体日程的最小行动单位，但不是具体时间块。

Todo 应尽量拆到一次可以独立完成。只有以下情况才让同一个 Todo 对应多段计划投入：

- 初始估时不足，需要继续完成同一个行动；
- 行动无法再按语义合理拆分；
- 行动本身允许分段执行。

到达某个时间、ScheduleEntry 开始或结束，都不会自动改变 Todo 的业务状态。Todo 是否完成来自用户反馈或可信的进度核对。

## 2. Goal 的三种运行方式

按用户希望助理承担的管理职责分类，结合目的与行动形态判断：

| 类型 | 主要管理什么 | 判断依据 |
| --- | --- | --- |
| `linear` | 一次性交付过程 | 不同阶段与行动逐步通向最终成果，完成后结束 |
| `recurring` | 每期重复交付 | 每轮有可独立判断的成果；频率和流程可先待定，再形成周期规则与模板 |
| `habit` | 重复行为的持续安排与维持 | 按频率持续安排相似行动，并随实际情况调整；可以服务一个明确的最终目的 |

有数字目标、明确终点或期望期限，都不足以单独判成 Linear；出现“每天/每周”也不足以判成 Habit。单个行动可以是独立 Todo；具体安排、禁排限制与日常作息按时间规则 §1.2 分类。

把“为了什么”和“主要怎么推进”一起理解。例如为了改善体能规律跑步、为提升词汇量持续练习，需要助理持续安排和维持这些行为时可以用 Habit，并把目的写进同一个 outcome；不用仅因出现结果目标再建一个 Linear。一次性网站上线仍按交付过程使用 Linear，每期发布一期节目使用 Recurring。

已有事实足够时直接归类；只有不同解释会实质改变管理方式且意图未明时，才围绕这个区别澄清，不让用户选择内部类型。真实存在独立交付、验收或需要另行管理的总体成果时保留它，不能为减少 Goal 数量而丢失要求。

循环目标包含准备、专项节点或临时直属任务，并不因此变为 mixed。`mixed` 只是输入包含不同管理需求的提示，不是正式类型，也不意味着自动拆分；只有各部分确需独立管理才拆 Goal。v0 不引入 Workstream 或新的目标层级。

## 3. 从用户输入建立结构

### 先定位，再创建

用户输入是了解现实的线索，不默认是完整计划。处理任何新输入时，先理解用户想得到什么、为什么现在做、它和其他事项是什么关系，再决定正式对象；不得因为输入中出现日期、时刻、会议或重复频率就直接跳到时间分类。

处理新输入时，先结合当前对话和正式计划判断它是：

- 对已有 Goal、Node 或 Todo 的补充或修改；
- 一个新的 Goal；
- 一个没有上层归属的独立 Todo；
- 按时间规则分类的具体安排、禁排限制或作息信息；
- 只作为背景，不需要建立正式对象的信息。

解析“它”“那个任务”“明天的安排”等指代时，同时使用当前对话和正式计划。无法可靠定位且错误定位会改变任务去留或计划可执行性时，不要猜测；按确认权限规则进行最少必要追问。

### 首次主动发现与后续局部发现

首次整体规划的广度扫描、分支追问及停止条件由 [发现规则 §1～4](discovery-loop.md) 维护。用户第一批输入只是入口，需保留全部近期相关方向；明确局部事项复用已有背景，不重新询问完整生活领域。

本文负责下文的对象与关系判断。局部语义检查可使用已有事实，不一定产生提问或完整发现循环；直接表达与新增业务推导的授权边界见 [确认规则 §6](decision-and-confirmation.md)。出现相关无归属依赖链、会议准备/跟进或重复行为意图不清等信号时，按发现规则 §6 局部修复。无关旧链不阻塞操作，审计也不强制建立 Goal。

### 检查共同目标与中间成果

用户先给出清晰结果时，从 Goal 识别近期需要达成的中间成果，再组织可执行 Todo。对 Linear 和 Recurring 都检查：哪些行动共同产出一个结果，哪里需要验收，后续依赖什么。用户未使用“阶段/节点”术语不代表不存在这些成果。

例如“网站上线”可按方案确认、可用版本验收、正式上线组织；“持续经营播客”可同时包含普通节点“设备升级完成”、每期节点“首期发布”和直属任务“回复合作邀约”。节点用成果命名，outcome 表达可判断的结果；不把研究、沟通等活动类别直接当成成果。长期目标不能因眼前只清楚首期或准备工作而被替换为一次性阶段目标。

信息逐渐明确时，可以把原任务归纳到新增节点，保留其 ID、进度和日程。只拆近期必要范围，不为了建节点补造远期流程；新业务推导按确认规则处理。

用户先给出零散行动时，必须检查它们是否共同推进一个已有或可合理归纳的结果。以下任一信号都应触发检查：

- 时间相邻，或用户用“然后、接着、之后、到时候”等方式连接；
- 涉及同一项目、材料、交付或协作链；
- 后一事项可能依赖前一事项的结果；
- 参与者存在汇报、审批或决策关系；
- 多个行为可能服务同一健康、学习、工作或生活结果。

检查可以得到三种结果：明显相关时定位已有 Goal 或提出候选共同 Goal，并识别其中有意义的中间成果；可能相关但信息不足时，带着候选理解追问；确实独立时保留为独立 Todo 或交给时间规则分类。强制的是完成检查，不是一定创建上层对象。

不得为了结构完整而虚构 Goal。后续识别出真实归属时，在原 Todo 上补充归属，保留其身份、状态以及已有日程关系。

### 会议、评审、汇报与沟通

开会、对进度、汇报、评审、过材料、和老板沟通或复盘既可能是目标路径中的行动，也可能只是独立占用。固定时间本身不能决定对象类型。遇到这类输入时，至少检查：

- 它推进什么结果；
- 会前需要准备什么；
- 会中需要确认、决定或交付什么；
- 会后是否可能产生修改或跟进；
- 它与前后会议是否属于同一目标路径；
- 所有这些交付和沟通最终希望促成什么业务结果、决策、验收或状态变化；
- 这条工作线之外，当前及下一计划窗口是否还有其他会争夺时间的项目或例行责任。

如果会议结果需要跟踪，将它作为 Todo，并可在 Schedule 中放到固定时间；如果只需记录安排并保护时间，交给时间规则作为 `commitment` TimeConstraint。不同解释会改变任务结构时先追问，不能只录入会议时段。

### 工具性重复行为与潜在目标

按 §2 判断需要持续安排重复行为、推进每期交付，还是仅记录具体安排或禁排时段；后者及作息信息交给时间规则。完成情况的反馈方式不决定对象类型；完成状态以实际反馈为准，未反馈不代表已完成。

习惯的目的可以直接记入其 outcome。只有用户明确要求另行管理总体结果、多条行动路径需要独立统筹，或已有正式目标确实相关时，才考虑独立结果目标与共享行动。骑行可能是通勤占用，也可能是改善体能的习惯；知道目的后不默认创建第二个 Goal，也不例行扩展到饮食、称重等未请求的事项。

首次整体规划仍按发现范围检查主要责任，局部请求则只检查本次近期明显缺口。已经作为 Habit Todo 排期的同一次行为不再复制为 TimeConstraint；真实共享行动见 §4。

### 控制首次建模深度

首次输入即使很短，也先弄清事项含义、预期结果和会改变近期行动的必要时间信息，不要擅自建立过大的任务结构。

可以提出为近期推进所必需的后续候选 Node，也可以在发现上层目标后检查明显缺失的近期行动，但不要一次性拆解与近期执行无关的远期细节。Goal 没有正式 DDL 时仍可建立结构，并创建“诊断问题、确认时间、收集信息”等真实近期行动；不能伪造完整倒排计划。

### 何时可以形成结构方案

发现范围及停止条件按 [发现规则 §4～5](discovery-loop.md)；任务结构还须达到以下语义结果：

- 新 Goal 能表达预期结果，目的和动机足以解释当前结构；
- 独立 Todo 可以直接开始且独立判断完成，无需强造上层 Goal；
- Recurring 的持续交付意图和当前要处理的工作明确即可，未定频率、锚点或模板不阻塞现有工作；按规则生成后续各期才要求满足 §8。Habit 仍需足以形成周期、锚点和最低次数方案的信息；
- 明显相关事项已检查向上归纳、归属和依赖，所需近期 Node、Todo、工作量假设可被解释；
- 影响近期结构的真实进度和硬 DDL 没有高影响歧义。

达到门槛后，工作量、执行模式、弹性时间窗和优先级等低风险推导组成整体方案让用户纠正，不再逐字段追问。远期未知不影响本周时说明理由，进入近期计划再补充。是否需确认及能否写入按 [确认规则 §6](decision-and-confirmation.md)，不是用户只说了动作名称就可自行选择完成标准。

## 4. 归属、共享和依赖

任务结构不是严格树。一个 Todo 可以没有上层归属，也可以同时推进多条 Goal/Node 路径。

### 独立 Todo

没有 Goal 或 Node 归属的行动是独立 Todo。独立不等于临时、低优先级或不重要，也不要求系统随后必须为它补一个 Goal。

### 目标直属 Todo

行动服务某个 Goal，但不属于某个节点时，直接关联 Goal，`node_id` 为 null。Linear 和 Recurring 均允许；它有明确目标归属，不是无归属的独立 Todo。循环目标的普通节点、直属任务与每期工作共同参与排期，不因到达新周期而复制或清除。

### 共享 Todo

当同一个行动同时推进多个 Goal 或 Node 时，只建立一个共享 Todo，并保存多个有效归属。完成一次即可推进全部有效路径；不得因为归属数量增加而复制 Todo、工作量或同一次计划投入。

用户确实独立管理两条结果路径时，Habit Todo 也可以同时服务 Habit Goal 和另一条普通 Goal/Node 路径；仅表达习惯的目的不需要建立共享结构。例如一次骑行既计入骑行习惯周期，也推进减重目标；保留一个 Todo 和一次计划投入，通过多个 `parent_refs` 表达两个作用。具体字段合法性读取数据合同。

### 修改归属

- 解除一条归属时，只移除对应关系；仍有其他归属时，不改变 Todo 状态。
- 删除最后一条归属但行动仍需执行时，将它保留为独立 Todo。
- 只有行动本身不再需要时才取消 Todo。
- 最后一条归属被移除且行动是否仍需执行不明确时，必须追问，不能把“解除归属”自动解释成“取消行动”。

### 依赖

依赖只表达“必须先完成什么，后续行动才可开始或成立”，不要把一般相关性、推荐顺序或同一 Goal 下的并列关系写成依赖。

Node 可以依赖前置 Node，Todo 可以依赖前置 Todo。共享 Todo 的依赖和完成结果同时作用于它的全部有效归属路径。依赖如何改变有效可排窗口和传播重排影响，读取时间规则与重新编排规则。

## 5. 通用生命周期

### 对象保留与有效归属路径

“对象仍保留在正式计划中”和“对象当前参与排期”不是同一件事。完成、暂停或取消不会自动删除 Goal、Node、Todo 及其已有事实。

对共享 Todo 而言，一条归属路径只有在以下条件同时成立时，才是当前排期使用的有效路径：

- Goal 处于 active；
- 如果路径包含 Node，Node 尚未完成或取消。

暂停、完成或取消的路径暂不贡献当前排期使用的 Goal 优先级和上层 DDL，但原始归属和历史事实继续保留。共享 Todo 只要仍有其他有效路径就继续运行；如果全部非空归属路径都失效，则保留 Todo，但暂不排期。独立 Todo 不依赖上层路径，按自身状态处理。

### 完成

- Linear Goal 和 Node 分别依据自己的 `outcome` 判断完成。用户明确报告该结果已达成，或可信进度事实已充分覆盖整个结果时，可以直接更新，不要求额外一轮确认。
- 当前已列出的子项不一定覆盖整个结果。子项全部完成只提供完成证据，不能自动推出父级完成；尚有未拆分范围、未完成交付或验收时，父级保持未完成。没有有效 Todo 也不代表 Node 已完成。
- 用户只报告部分或全部已列子项完成时，先更新这些明确事实；父级结果未知不阻塞这次局部更新，也不强制补建后续或历史任务。只有当前请求确实需要判断父级是否完成且证据不足时，才询问缺失的结果事实。
- Node 下的 Todo 默认都是必要行动。取消其中一个 Todo 表示该行动不再必要，此时重新检查 Node 是否仍可成立、需要重新拆解或应被取消。

完成判断使用既有 `outcome`，不为 Node 新建另一套独立完成公式。

### 暂停与恢复

暂停 Goal 时：

- 保留 Goal 及其既有任务事实；
- 停止生成新的周期实例；
- 只移除由该 Goal 单独驱动的未来日程；
- 共享 Todo 如果仍有其他有效路径，不随该 Goal 一起停止。

恢复 Goal 时，重新评估所有尚未完成的普通节点、直属任务和已有每期工作；周期生成仅处理当前周期以及本周规划窗口内随后进入范围的周期，不补已经结束的暂停周期。规则未齐时保留现有工作，周期实例按原稳定身份复用，不重复生成。

恢复 Linear Goal 时，重新启用原有未完成 Node 和 Todo，使其重新进入待排判断；不要因为恢复而复制任务结构。

### 取消与永久停止

取消 Goal 时，只服务该 Goal 的未完成 Node 和 Todo 一并取消；共享 Todo 仍有其他有效路径时继续保留。

只有用户明确取消某个阶段，或经确认的任务结构调整认定该阶段不再需要时，才取消 Node。取消 Node 时，只服务该 Node 的未完成 Todo 一并取消；共享 Todo 只解除这条 Node 归属，仍有其他有效归属时继续保留。

Recurring 和 Habit Goal 永久停止时进入取消状态，而不是完成状态。停止后不再生成新周期，但保留循环规则、模板、习惯规则、已经形成的历史事实和既有周期身份。

## 6. 修改与纠正

用户补充信息、纠正理解或改变归属时，优先修改原对象，不要因为描述变化就复制 Goal、Node 或 Todo。

修改 Goal 或 Node 的 `outcome` 时：

- 如果只是更准确地描述同一结果，且不影响下层结构，可以保留现有 Node、Todo 和关系。
- 如果结果变化导致行动新增、删除、替换或重组，应形成整组结构变更，并由确认权限规则判断是否可以提交。

只有行动语义已经变成另一件可以独立完成的事时，才拆成新的 Todo。对象被取消不等于从正式计划中抹除；保留它已有的身份和历史事实，未来日程如何清理由进度或重新编排流程决定。

## 7. Linear Goal

Linear Goal 有明确终点。主动识别通向终点的中间成果、验收与依赖，按 §3 建立有意义的普通节点和近期行动。节点完成核对自己的 outcome，目标完成核对最终 outcome；已有子项完成不替代未覆盖范围或最终验收。简单任务可以直属目标，不按固定层数拆分。

## 8. Recurring Goal

Recurring Goal 表达持续重复交付的意图。它可以同时包含普通节点、每期节点和目标直属任务；只有每期节点参与循环生成。完成某期或普通专项只完成该 Node，Goal 继续 active。

### 建立目标与逐步确定规则

可以先建立 Goal 和已明确的当前工作，再确认频率、首个周期和稳定流程。未知字段按合同留空，已知部分保留；不为通过校验编造周期、精确 DDL 或模板，也不因频率未知改成 Linear。当前任务可直接排期，缺少未来规则不代表当前结构未就绪。

首期可以先建立 `cycle` 节点且 `cycle_starts_on` 为 null；准备或试制成果也可以是 `regular`，按实际成果含义区分。实际可开始日期 `starts_on` 与硬 DDL 独立表达，不拿周期末尾充当截止要求。

### 模板与周期实例

只有 active Goal 的间隔、单位、首个周期锚点和完整模板齐备，且既有未绑定每期节点已处理后，才按规则推导后续实例。没有 DDL 也可以生成：节点 deadline 为 null。模板只定义每期节点及其行动，不包含普通节点和目标直属任务；不把临时试做流程自动固化成模板。

周期开始日从原始锚点直接计算；月末使用目标月最后一天，下一期仍从原锚点推导，不逐次累加造成漂移。周期范围到下个周期开始前，不依赖 deadline；已确认的首期 DDL 若存在，按同一原锚点偏移推导后续 DDL。

每个缺少的周期按模板一次性生成 Node 和全部 Todo；重复操作复用 `(goal_id, cycle_starts_on)`，取消节点仍占用身份。只生成与当前自然周 planning_window 相交的正式周期，跨周继续复用。周期结束不自动取消仍需完成的工作，已有未完成 Todo 继续按进度规则处理。

### 补齐规则与修改范围

启用或改变规则前，先定位已存在的首期/试制：用户事实已说明其关系时直接沿用；否则只澄清它是否计入新规则及对应哪一期。纳入时给原节点绑定周期身份，必要时把未绑定的普通试制节点改成 cycle；保留原 Node、Todo、进度和 ScheduleEntry，不用模板重建它。

不纳入的试制保留为 regular。尚未解决的未绑定 cycle 不得靠标题或日期猜测归属，也不得一边保留歧义一边生成可能重复的实例；这只阻塞相关自动推导，不阻塞已明确工作的排期。

- 普通改期只改实际开始/截止或日程，不改绑定的周期身份。修改未来规则保留历史和已生成实例；新规则从明确的未来边界生效，不按新锚点追溯补造旧期。
- 只改本期时改实例；用户确认以后各期也如此时才改模板，默认只影响尚未生成的周期。同步已有周期需展示影响并按确认规则处理。
- 普通节点和直属任务始终独立于模板生成；允许与每期工作建立真实依赖，不复制共享行动或投入。

## 9. Habit Goal

Habit Goal 持续维护每个考核周期的最低完成次数，不生成 Node。每次实际执行机会由独立的 Habit Todo 表达。

`outcome` 记录用户希望达到或维持的结果，例如“通过规律运动改善体能”；有明确数值目的时如实保留，没有时不要求量化。`habit_rule` 记录行为频率、时长与偏好，并据此判断周期达标。不要把 outcome 只写成规则的重复，也不因最终目的单独复制一个 Linear Goal。

期望观察期限可以随目的保留在 outcome/context，不自动变成每次行动的硬截止。真实硬交付承诺不能藏进背景或为了套 Habit 而丢弃，按 §2 检查是否还需独立管理交付。

某周期次数达标不证明最终结果已达成；用户报告最终结果时保留其事实，是否继续、调整或停止习惯按实际意图处理，不自动修改为 completed。没有特殊终点的维持型习惯同样成立。

### 周期生成

只有 active 的 Habit Goal 才生成周期 Todo；同一周期内的重排不得触发新一批生成。

请求正式排期时，先按规则识别与当前自然周规划范围相交、且尚未结束的相关周期，检查已有 Habit Todo，再补齐缺少的实例。以 `(goal_id, habit_period_starts_on, habit_occurrence_index)` 复用身份；重复排期不产生新一批，已完成或已取消实例仍占用原身份，取消不自动补次数。

每个周期默认形成 `minimum_count` 个 Todo，不自动生成备用次数；用户明确增加的次数单独保留。只生成当前自然周规划窗口需要的正式 Habit Todo，不提前生成以后各周；跨周周期继续复用已经生成的同一批实例。仅记录习惯结构、起点尚在未来或只查询时，不要求现在展开远期 Todo。

已有习惯规则本身不代表已经安排；准备排期时不得因为当前 todos 为空而遗漏整个 Habit。实例准备好后进入 scheduling 的统一待排分组，不强行排满未来频次或忽略未排原因。

`session_minutes` 只用于生成 Habit Todo 的初始估时。后续调整某个 Todo 的剩余估时，不得反向修改整个 Habit 的默认单次时长。

### 长期偏好与本期窗口

Habit 专属、需要跨周期复用的偏好星期和偏好时段属于 Habit 长期规则：

- 默认作为软偏好，排期应尽量满足，但不满足不代表计划非法；
- 用户明确表达“只能”“必须”等要求时，才作为硬约束；
- 只影响当前周期的临时变化写在本期 Todo 的可执行窗口中；
- 用户明确表示“以后都这样”时，才修改长期规则；
- 用户对所有任务普遍适用的作息仍属于 AvailabilityRules，不要写成某个 Habit 的专属偏好。

具体字段由数据合同定义，软硬偏好如何选择时间由排期规则定义。

### 增加、未完成和达标

- 用户要求本周期额外增加一次时，创建下一次 Habit Todo，但不自动提高以后周期的 `minimum_count`。
- 只有用户明确修改长期最低标准时，才更新以后周期的 `minimum_count`。
- Habit Todo 未完成时，优先重新编排原 Todo，不创建替代 Todo。
- 周期结束仍未完成时，允许该周期不达标，不自动补次数到下个周期。
- 本周期已完成次数达到 `minimum_count` 即视为本周期达标；Goal 本身仍保持 active，不因一次达标而完成或暂停。
